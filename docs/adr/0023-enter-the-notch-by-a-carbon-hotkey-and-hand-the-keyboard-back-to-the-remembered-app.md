# Enter the notch by a Carbon hotkey and hand the keyboard back to the remembered app

Accepted on 2026-11-13 (#427). Before this, the only way to give the notch panel keyboard focus was a click: automatic presentation never makes the panel key, and Tab cannot reach a non-activating panel in another process. The user agreed one system-wide entry key, ⌃⌥Space by default, changeable or switched off in Settings › Notch, with plain digits never taken from other apps.

## Decision

- **Registration.** `NotchHotkeyRegistrar` registers the one shortcut with Carbon `RegisterEventHotKey` and `kEventHotKeyExclusive`. It needs no Accessibility permission and sees only that key combination. Herdly installs no event tap and no global `NSEvent` key monitor. `eventHotKeyExistsErr` is shown under the Settings row and the notch stays click-only; a recorded shortcut must hold Control, Option, or Command (`NotchHotkey`), so ordinary typing can never be claimed.
- **Entry without activation.** On a press, Herdly remembers the frontmost app and makes the panel key the way a click does (`hasDeliberateKeyboardFocus`), without activating Herdly. Herdly activates itself only when the window server refuses key status to an inactive app. `NotchKeyboardEntry.target` sends the keyboard to the card on screen, or opens the queue with its top row selected.
- **One hand-back path.** The hotkey again, Escape at the top level, and the panel folding for any reason go through `Companion.handBackKeyboard()`, and `NotchKeyboardReturn.handBack` (HerdlyCore) picks what to activate:
  - the remembered app, matched by process identifier and bundle identifier, while it still runs;
  - nothing, when it has quit, so macOS chooses; Herdly never activates a terminal it guessed;
  - nothing, when a third app came forward meanwhile (for example an Open from the notch), so that app keeps the keyboard;
  - nothing later, once the panel lost key status to another app, because the remembered app is forgotten then.
- **Hold and placement.** The queue the hotkey opened stays open while it holds the keyboard and does not move displays. Focus from a click still holds nothing (#376), and keyboard focus still pauses no countdown (ADR 0020). Amended for spotlight cards on 2026-11-13 (#428), below.

## Considered options

- **Event tap (`CGEventTap`) or global `NSEvent` key monitor.** Rejected: both need Accessibility or Input Monitoring permission and observe every keystroke, far more than one shortcut needs. The issue forbids an event-tap fallback.
- **Activate Herdly on every press.** Rejected: every hand-back would then depend on re-activating the other app correctly, and a failed or raced activation would leave the user typing into nothing. Taking key status like a click keeps the user's app frontmost.
- **Always re-activate the remembered app.** Rejected: after Return opened a session in another app from the notch, folding would pull the original app back over the one the user just asked for.
- **Non-exclusive registration.** Rejected: Carbon then accepts a shortcut another process already holds, so Settings could not report it as taken.

## Not yet shown live

- ⌃⌥Space from Ghostty mid-line, then again, with the next keystroke landing at the same cursor.
- A shortcut held by another app reported as taken in Settings.
- A shortcut claimed through System Settings, which Carbon cannot see; it may register without error and never fire (recorded under Boundaries in docs/notch-placement.md).

## Amendment 2026-11-13: a focused spotlight card is held (#428)

Agreed with the user on 2026-11-13 (Paper L "Spotlight question by keyboard", frames 1–8). #427 left a spotlight card that had the keyboard to close at its card-open time; a user picking an answer could lose the card mid-answer.

- **Hold.** A spotlight card holds open while the panel has deliberate keyboard focus, from the hotkey or a click, however long the user takes, until it hands back, as hover does: `NotchPresentationController.update(keyboardFocus:)` treats focus like interaction for the spotlight only, and its card-open time starts over once focus leaves. A clicked queue still folds when the pointer leaves (#376 is narrowed only for spotlight cards), and `NotchInteraction.isActive` is unchanged, so placement and every other rule read focus as before.
- **Countdown.** Focus pauses nothing. Approval and Claude question deadlines still read the pointer only (ADR 0020 unchanged). When a Claude question's countdown ends with its card focused, the card hands back with no answer (`SpotlightKeyboardCard`) and the keyboard hold ends (`update(keyboardHoldEnded:)`): from then on the card follows its normal spotlight open time, as if focus had just left. While it is still visible and focused, its digits stay inert and Return opens Claude; when it folds, the keyboard goes back through `Companion.handBackKeyboard()`. A half-made selection is never sent.
- **Wait.** While a spotlight card has the keyboard, `acceptsAgentSpotlight(keyboardFocus:)` refuses a fresh card. A new approval or question waits behind it, named in one line (`SpotlightKeyboardWait`), and takes the spotlight after Send or Escape. Its own deadline keeps running.
- **Keys.** One table, `SpotlightCardKeys`, maps every key for a question card with or without the keyboard (`SpotlightCardFocus`): only Return on a card Herdly can answer reaches its Next or Send, and only while enabled; O, X and ← → act as Open, Dismiss and ‹ › only on a card that has the keyboard, and O opens only where the card shows Open. The hotkey makes the panel itself first responder, so a digit selects rather than typing into "Or type an answer". Keys still reach the panel only once it is key, so typing in another app never reaches the card.
- **Sent.** A send the route records (`RowNote.sending` or `.awaitingCodex` from the user's own action) shows "Sent to <agent>: <n> · <label>" for one second (`SpotlightKeyboardCard.sentHold`), then the panel folds through `Companion.handBackKeyboard()`. The card and its line stay for the whole second even if the question leaves the queue meanwhile (`keepsSentCard`). The timer only folds; nothing is sent on a timer.
- **Keys on a clicked card (2026-11-13, #438).** A question card opened from the queue (a click, or Return on the hotkey queue's selected row) that has deliberate keyboard focus reads the same keyboard row of `SpotlightCardKeys` (`SpotlightCardFocus.clickedWithKeyboard(answerable:)`): answering while Herdly can answer it, read-only otherwise, and the same key labels. It gets none of the spotlight's hold, wait, sent line, foot line or ring: Send still returns it to the queue at once (D10), and a countdown that ends leaves it read-only. Focus still pauses nothing.
- **Keys on an approval card (2026-11-13, #439).** An approval card with deliberate keyboard focus (a clicked card, the hotkey's queue then Return, or a focused spotlight) takes ⌘⏎ for Approve, ⌘⌫ for Deny and O for Open, through one table, `ApprovalCardKeys`. A keyboard decision is the user's explicit allow-once or deny choice, the same as a click: it is taken only while Approve and Deny are shown and enabled, and goes through the same `decideAgent` call and live check. Bare Return, other letters, digits and bare Delete never decide; past the deadline, handed back, or on a request that stays native, only Open remains (O or Return). The keys are received by Herdly's own panel and never reach the agent or a terminal, so ADR 0006's Ghostty keystroke exception, which concerns keys sent *into* a terminal and permits no keystroke approvals, is unchanged. Focus still pauses no deadline (ADR 0020).
- **The to-check walk (2026-11-13, #440).** From the hotkey's queue → opens the first to-check item as its card (`NotchPresentationMode.walkCard`), and ← → walk the rest one card at a time (Paper K "D · Walk the to-check list"; owner decisions of 2026-11-13: board K's open question "Walk", and option A for questions). The rule is one HerdlyCore value, `ToCheckWalk`, held by `NotchPresentationController` and fed the open queue's rows on every refresh: the queue's own order ("By need" or "Newest first"), so live approvals still come first, without running work or Earlier results; an arrival takes its queue position and the count follows; on a card with several questions ← → step that card's questions before moving to the previous or next card; the ends stop without wrapping. The walk is held by the hotkey's keyboard focus like a card opened from that queue, and refuses a fresh spotlight, which joins the walk at its queue position instead. Stepping past, opening a card, or reaching an end acknowledges nothing: only X on a result, a decision, an answer, or the existing acknowledgment rules clear an item, and the walk moves on only once that item has left to-check (a decision on a walk card does not return to the queue, D10 is for clicked cards). When nothing is left the panel says "All checked" for `ToCheckWalk.allCheckedHold` (one second, the sent line's hold) and folds through `Companion.collapse()` and `handBackKeyboard()`; the timer only asks for a refresh. Escape returns to the queue with that item's row selected (`NotchEscape.walkToQueue`). Each card keeps its own keys; the walk's result card adds O and X through `ResultCardKeys`, with deliberate focus only. Focus still pauses no deadline (ADR 0020).
- **Return target and VoiceOver.** The foot line names the app `NotchKeyboardReturn.target` would return to, the same decision `handBack` spends, so the two cannot differ. VoiceOver announces the question on screen whenever a card takes the keyboard, by the hotkey or a click.

### Considered options

- **Hold only for hotkey focus, not a click.** Rejected by the user: a click gives the same keyboard, and a card that folds under a user who clicked into it to answer is the bug #428 fixes.
- **Pause the Claude countdown while focused.** Rejected: ADR 0020 lets only the pointer pause a deadline, never past 2 minutes; a keyboard hold with no bound would let a forgotten card stall Claude.
- **Let an arrival replace the focused card.** Rejected: the user's next digit would land on a card they had not read.
