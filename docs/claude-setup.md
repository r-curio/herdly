# Claude setup

Claude setup is explicit and scoped to one configuration root. The default root is `~/.claude`; an alternate root selected from **Agents → Claude Code** is kept independent. Herdly never scans for accounts or credentials and never merges roots.

The preview and install own one packaged `HerdlyHook` copy, one set of hook entries in that root's `settings.json`, and ensure `env.CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1`. Herdly records that environment key as owned only when it had to add it; a pre-existing matching value remains user-owned and is preserved through repair and undo. The title hooks return Claude's supported JSON `terminalSequence` response: `SessionStart` sets `Herdly Claude <full-session-id>` for exact Ghostty matching and `SessionEnd` requests a title reset. They never write the OSC sequence as plain hook stdout. Herdly does not install a launcher, change permission rules, or restart Claude sessions.

The installed hook set observes session, prompt, tool, Bash, file, and web permission, subagent, notification, stop, and session-end events. A separate `PreToolUse` matcher for `AskUserQuestion` lets Herdly relay one human-selected single choice, multi-select, or typed answer through Claude's documented `updatedInput` response while the exact helper is live. One exact live Bash permission, one exact file request (`Edit`, `Write`, `NotebookEdit`, or `Read`, in its own `PermissionRequest` entry matching `Edit|Write|NotebookEdit|Read`), or one exact web request (`WebFetch` or `WebSearch`, in a further entry matching `WebFetch|WebSearch`) can receive Approve once or Deny through a short-lived receipt and decision record. A request whose input differs from the shapes proven in [claude-file-approvals](evidence/claude-file-approvals.md) and [claude-web-approvals](evidence/claude-web-approvals.md) gets no request token and stays in Claude's dialog. A root configured by an earlier release keeps working without the newer entries; its Controls card explains that Configure Claude adds them, and until then those requests stay native. The helper acknowledges the decision only after emitting Claude's response; a missing acknowledgment is reported as uncertain and never as execution proof. The helper emits no decision when Herdly is absent, the request is ambiguous, the deadline passes, or the user hands it back, so Claude's native prompt remains the fallback. The hook timeout covers the five-second connection wait and 30-second decision window. Plan-exit, MCP, persistent allow, and keystroke approvals stay native. The optional usage bridge is offered in the same preview and is off by default. Selecting it records the intent but does not edit `statusLine` until the compatibility probe passes; the core connection remains independent. The usage contract and proof boundary are documented in [Claude usage](claude-usage.md), and the bounded event payload, live question channel, and queue rules are documented in [Claude observations](claude-observations.md).

Question answers are fail-closed. Herdly validates the installation, normalized Claude configuration root, separate event directory, session, prompt, tool-use, and fresh helper request identities, rechecks the helper-owned liveness marker immediately before writing, and spends the in-memory helper token before writing one answer. The helper emits a matching delivery acknowledgment only after Claude's response is written; a missing acknowledgment removes the unconfirmed answer and never reports it as sent. Only a receipt issued by this running companion makes a question answerable. Herdly keeps the receipts it issued, the tokens it spent and each question's hover hold in process memory across a scan that misses the question, so a rescan that finds its own identical receipt already on disk re-adopts it until the held deadline (never past two minutes from publish) instead of leaving the card read-only, and a pause still under the pointer resumes with the time it had left (#385); a spent token is never re-adopted, and a receipt left on disk by a previous launch or another process, or one that no longer matches the request's installation, root, event directory, publish time or window, is never adopted. Expiry, malformed input, helper loss, uncertainty, or restart send no answer; Claude's native question remains authoritative when delivery is not confirmed. A call of one to four questions is answered as one set: the answer record carries one entry per question in order, the helper accepts only a complete set matching every question's own options, and it emits `updatedInput.answers` keyed by each question's text (#382; Paper "G · Claude: answer several questions", https://app.paper.design/file/01M5BZ6XS02TKJWZ4CF0MVYBNW/p-1-0). A partial, mismatched, late, or repeated set sends nothing. A call with more than four questions, any question without readable text, a secret question, or two questions with the same text (Claude keys answers by question text) is not published, so its card is read-only and the call stays in Claude, as do options from an incomplete option list (a typed answer is still offered). A one-answer record also writes the pre-#382 `kind` and `answer` fields so a helper from an older build still reads it; a larger set omits them, so an older helper cannot decode it and sends nothing.

The preview lists every affected `settings.json` field with its matcher, exact helper command, timeout, and owned environment value. It also lists the selected settings file, helper, event-record directory, install record, and backup directory. It does not display the complete `settings.json` or unrelated settings and credentials. Herdly reads the root's session registry (`<CLAUDE_CONFIG_DIR>/sessions/<pid>.json`, one entry per live Claude process) and falls back to `claude agents --json` in a bounded subprocess with the selected `CLAUDE_CONFIG_DIR` when the registry is absent or unusable; Claude Code 2.1.292 no longer accepts `--json`. Registry entries are raw process state: Claude rewrites them in place and leaves them behind after exit. An entry counts only while its PID is running (not a zombie) and, when Claude recorded `procStart`, that process started at the recorded UTC time, so a reused PID never revives a session. A torn entry is re-read a bounded number of times; one still torn from a live process makes the inventory unavailable, and one from an exited process is ignored. `interactive` entries (or entries without a `kind`, which Claude treats as interactive) become interactive rows. A `bg` entry holds a session that was parked and continued as a background job; since #393 (2026-11-10) it becomes a background row with its `name`, `cwd`, `startedAt`, `statusUpdatedAt` and status (`busy`, `waiting`, or `idle`, with `shell` read as `idle` and any other status kept unknown), so a running job is listed as live with its name and is never read as ended. Its process runs under Claude's pty host, not in a terminal tab, so the row names no PID and is never a target for Open, visits or input. A `bg` entry is not a duplicate of an interactive holder: a session with an interactive row keeps that row alone, and a session two `bg` entries hold, or one whose entry lacks a readable `cwd`, `startedAt` or `name`, is only marked as background (still live, without a row). Only the `bg` entry's session ID is required; its other fields never make the inventory unavailable. `daemon`, `daemon-worker`, and parked-job entries are skipped, and an unknown kind makes the inventory unavailable. Once the `bg` process exits, or its PID no longer matches `procStart`, the session is no longer listed and the usual ended rules apply. A parked interactive entry whose `parkedJobId` matches one `bg` entry's `jobId` names the process that displays that background session, which only the herdr pane binding uses ([ADR 0008](adr/0008-bind-herdr-panes-when-herdly-and-herdr-agree.md)). The `shell` status, which Claude writes when the prompt is idle while a background Bash task keeps running, is read as `idle`. When both sources fail, the registry's failure is reported. Either source is bounded and then validated the same way: Herdly validates the top-level array, canonical full session IDs, nonempty shared `cwd`/`name`/`startedAt` fields, supported kinds, lifecycle fields, and duplicate identities, then keeps only typed restart status for setup. The same typed snapshot is polled off the main actor for configured roots and contributes only generic lifecycle rows to the shared agent queue. Interactive status and background state are decoded independently; a background terminal state wins over a stale status. It never uses `cwd` or `name` as identity or targeting evidence. An active session counts as needing restart only when it started before installation and has no newly observed startup delivery; sessions started after installation or already observed by the exact startup hook are not counted. A disabled, failed, timed-out, malformed, incomplete, or duplicate inventory is reported as unavailable; Herdly never treats it as an empty root, never persists the inventory payload, and does not clear stronger hook evidence.

Herdly configures the selected user root. Claude can also merge project and command-line settings, and the supported CLI does not expose a per-key effective-settings resolver. Herdly fails closed for a detected `CLAUDE_CONFIG_DIR` mismatch or managed policy. Project context is not supplied to this setup snapshot, so project and command-line `--settings` values remain unavailable in the preview. The setup preview (**⋯ → Show Setup Changes…**) warns that arbitrary future project files or command-line `--settings` values may override the selected root; Herdly does not claim those values are absent or inspect the app's working directory as a substitute. It requires a new `SessionStart` event from the exact selected root before reporting Connected.

## States

- **Not configured**: no Herdly install record exists for the selected root.
- **Configured; restart required**: owned files are present, but Herdly has not observed a post-install startup event from this root. The card shows a **Restart required** badge and offers Configure Claude only when it would change something (settings left to write, or a changed usage choice). Sessions already running pick up the hooks and may report activity (observed live on 2026-10-20, [issue #299](https://github.com/r-curio/herdly/issues/299)), but only a new session sends the startup event and sets the terminal title Herdly uses to match its Ghostty tab. While any root waits, Herdly re-checks it on its regular scan, at most every five seconds, and the card switches to Connected once that startup event lands, without a relaunch or Review Again ([issue #364](https://github.com/r-curio/herdly/issues/364)).
- **Connected**: a newly received `SessionStart` event whose Claude `source` is `startup`, carrying this root's installation identity, was observed after installation. Resume, clear, compact, or other events from another root, another installation, another hook event, or before installation do not connect the root.
- **Repair required**: an owned hook or helper is missing.
- **Conflict**: an owned value changed, duplicate Herdly installs exist, or the install record is inconsistent. Herdly does not overwrite it.
- **Blocked by policy**: managed settings allow only managed hooks, or hooks are disabled.
- **Shadowed**: a higher-priority settings source wins; Herdly does not try to defeat it.
- **Unsupported**: the detected Claude Code version is older than the tested `2.1.273` baseline. Newer versions still need a fresh runtime event before they become connected.

Ghostty readiness is separate from connection health. A root can be connected while Ghostty controls are off or still awaiting Automation permission. Exact return is never attempted for stale, duplicate, overwritten, split, cross-window, or otherwise ambiguous targets; Open falls back to raising the session's terminal app instead ([ADR 0015](adr/0015-raise-the-terminal-app-when-open-cannot-reach-the-exact-target.md), below).

## Exact Claude tab return (#84)

Claude's **Open Session** action is shown for a canonical session that appears exactly once in every
complete configured-root inventory, unless Ghostty controls are on and still awaiting Automation
permission. Exact return selects one current unsplit Ghostty tab titled
`Herdly Claude <full-session-id>` in the front window. The action rechecks the root inventories, the
complete Ghostty inventory, the exact window/tab/terminal locator, and the selected front window
before it can acknowledge queued outcomes. A title match alone never acknowledges anything.

When the exact tab cannot be reached (#236, ADR 0015) — Ghostty controls are off, Ghostty is not
running, no tab or several tabs carry the title, the tab is split or in another window, or the
selection does not verify — Herdly walks from the session's registry PID up its parent processes to
the nearest app. If that app is a supported terminal and is running, Herdly activates it as a whole,
silently, without selecting a window or tab, acknowledging anything, or making it an input target. A
walk that fails or ends at another app, a session no longer in the inventory ("This session has
ended."), or an unreadable Ghostty ("Herdly can't read Ghostty. Check Settings › Terminals.") stays
unavailable. An actionable approval is handed back, with no decision, on a verified Open or a
fallback.

Acknowledgment follows [ADR 0016](adr/0016-open-and-acknowledge-visits-the-same-way-on-every-terminal-host.md)'s
one rule for every terminal host, the same as Codex tabs (#237). The tab is visible when macOS reports
Ghostty frontmost and Ghostty's front window has it selected, and its binding (complete inventories,
one live session, one unsplit tab carrying the full title, in the front window) still holds. A manual
visit is a scan that shows the tab not visible followed by one that shows it visible; it acknowledges
outcomes that arrived before the earlier scan, so one arriving between scans stays queued. An outcome
that arrives while the tab is visible is acknowledged once the tab has stayed visible for five
seconds after it arrived (the dwell rule); before #237 it stayed queued until dismissed. A failed or
missing scan, an incomplete inventory, or any uncertain target acknowledges nothing, and a restored
outcome in a tab that is already in front waits for a switch to it. A verified Open in Claude
acknowledges the outcomes that arrived before it; a fallback never does, and the scan interval spanning
any Open is never a visit.

Same-window return is supported. Duplicate live resumes and failed inventories remain unavailable;
missing titles, overwritten titles, split tabs, background Ghostty windows and changed locators fall
back as above. None sends terminal input or acknowledges. Ghostty Automation stays opt-in.
Background Claude sessions do not create separate queue rows or exact-tab warnings; only
interactive sessions can have a Ghostty target.

Automated coverage is in `Tests/HerdlyCoreTests/CLITests.swift`: canonical full-title matching,
duplicate and missing identities, overwritten and split titles, cross-window rejection before
selection, focus-transition timing, duplicate roots, and incomplete inventories. The focused and
full Swift suites cover source compatibility. Isolated live Claude/Ghostty return testing was
deferred by the operator and is not claimed here.

## Haiku session titles

Claude names a session it has not titled with a placeholder from its folder (`landbase-22`, registry `nameSource: "derived"`). This happens, for example, when a session opens with a slash command. The opt-in **Name sessions with Haiku** toggle on a ready root (off by default) lets the installed `UserPromptSubmit` hook replace that placeholder. The switch is the marker file `<events>/session-titles/enabled`; toggling it never edits `settings.json`.

Outside the `/clear` case below, the hook never waits on the model. On the session's first prompt that says something about the work (not empty, not a `<…>` message such as `<task-notification>`, not a bare slash command such as `/clear`), it records a pending attempt and starts itself detached as a generator. The generator receives the prompt's first 2,000 characters on stdin and runs one `claude -p --model haiku` call through the session's own Claude executable, with no tools, hooks, MCP servers, user or project settings, slash commands, or transcript. Its output goes to `/dev/null`, so Claude's wait for the hook ends when the hook exits. The generator writes a sanitized kebab-case title or records a failure. On any later prompt, the hook returns `hookSpecificOutput.sessionTitle` once, and Claude records the title with `nameSource: "hook"`. Herdly's queue shows that registry name.

The hook reads `<CLAUDE_CONFIG_DIR>/sessions/<CLAUDE_PID>.json` and acts only while that entry belongs to the hook's exact session and still shows the derived name. A `/rename`, a `--name`, or Claude's own AI title always wins, and an unreadable or mismatched entry does nothing. A `/clear` gives the process a new session but keeps its name, so a title Herdly gave the cleared session would otherwise stay: a `hook` name that equals a title Herdly applied to a different session counts as carried over, and the new session gets its own title the same way (observed with Claude Code 2.1.307, which applies a hook title whatever the current name's source). Because that carried-over title describes the previous conversation, the first eligible prompt after a `/clear` is the one exception to never waiting: it polls the record for up to eight seconds and returns the new title on that same prompt when it is ready, otherwise a later prompt applies it as usual. A fresh session's folder placeholder never waits. A name from `/rename`, `--name`, or Claude's own AI title still survives `/clear` unchanged. A failed generation, or one still pending after two minutes, is retried on a later eligible prompt, with at most two attempts per session. A single-prompt session therefore keeps its placeholder. Records live in `<events>/session-titles/<session-id>.json`, hold only status, title, and attempt count, and are pruned after seven days. Titles are presentation only and are never identity or targeting evidence.

Automated coverage is in `Tests/HerdlyCoreTests/ClaudeSessionTitlesTests.swift`. A disposable interactive session in a scratch folder, run with the development `HerdlyHook` through `--settings` and a scratch events directory, did the following on Claude Code 2.1.295. The first prompt was answered while generation ran, and the title was ready about four seconds after the session started. The second prompt changed the registry from `work-02` (`derived`) to `move-rooms-booking-sheet-to-scheduler` (`hook`). A direct hook run returned in 52 ms with empty stdout, and its generator exited after writing the title.

## Ownership and undo

Reinstall reuses the root's installation identity and recreates only missing exact entries. Herdly keeps the root's installed helper in step with the running app: at launch and on each setup refresh, when the bundled helper passes its self-test and differs from the installed copy, Herdly replaces the helper and updates the helper recorded in `install.json`, only while the installed file is still exactly the one it recorded. This never reads or writes `settings.json`, so the connection state and undo snapshots are unchanged. Configure likewise replaces Herdly's own unchanged helper with a newer bundled one instead of reporting a conflict. A helper that differs from the recorded one is never replaced and stays a conflict. Running hooks finish with the old helper; the next hook uses the new one. A changed owned handler or title environment value is a conflict. Undo restores the original `settings.json` byte-for-byte when it is unchanged; after unrelated edits it removes only unchanged Herdly-owned entries and the exact title environment key, preserving other settings and environment formatting. Missing or inconsistent state refuses guessed restoration and leaves targeted manual recovery to the operator.

Automated coverage is in `Tests/HerdlyCoreTests/ClaudeSetupTests.swift`. It uses temporary roots only; it does not modify the user's Claude or Ghostty configuration. The sanitized isolated startup run record and commands are recorded in [Claude setup live evidence](evidence/claude-setup-live.md). The run record proves that a newly started disposable session delivered the exact-root hook events; existing sessions are intentionally reported as requiring restart. A helper self-test proves both title JSON shapes and the metadata boundary. Ghostty title application, clean SessionEnd reset, and the live old-session restart-required observation remain deferred operator checks; none is claimed as passed here. Those checks also do not prove that project and command-line settings were absent. Claude only delivers `SessionEnd` on supported clean shutdown paths, so reliable abrupt-exit title restoration remains unproven without a launcher or equivalent terminal lifecycle integration.
