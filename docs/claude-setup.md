# Claude setup

Claude setup is explicit and scoped to one configuration root. The default root is `~/.claude`; an alternate root selected from **Agents → Claude Code** is kept independent. Steer never scans for accounts or credentials and never merges roots.

The preview and install own one packaged `SteerHook` copy, one set of hook entries in that root's `settings.json`, and ensure `env.CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1`. Steer records that environment key as owned only when it had to add it; a pre-existing matching value remains user-owned and is preserved through repair and undo. The title hooks return Claude's supported JSON `terminalSequence` response: `SessionStart` sets `Steer Claude <full-session-id>` for exact Ghostty matching and `SessionEnd` requests a title reset. They never write the OSC sequence as plain hook stdout. Steer does not install a launcher, change permission rules, or restart Claude sessions.

The installed hook set observes session, prompt, tool, Bash and file permission, subagent, notification, stop, and session-end events. A separate `PreToolUse` matcher for `AskUserQuestion` lets Steer relay one human-selected single choice, multi-select, or typed answer through Claude's documented `updatedInput` response while the exact helper is live. One exact live Bash permission, or one exact file request (`Edit`, `Write`, `NotebookEdit`, or `Read`, in its own `PermissionRequest` entry matching `Edit|Write|NotebookEdit|Read`), can receive Approve once or Deny through a short-lived receipt and decision record. A file request whose input differs from the shape proven in [claude-file-approvals](evidence/claude-file-approvals.md) gets no request token and stays in Claude's dialog. A root configured by an earlier release keeps working without the file entry; its Controls card explains that Configure Claude adds it, and until then file requests stay native. The helper acknowledges the decision only after emitting Claude's response; a missing acknowledgment is reported as uncertain and never as execution proof. The helper emits no decision when Steer is absent, the request is ambiguous, the deadline passes, or the user hands it back, so Claude's native prompt remains the fallback. The hook timeout covers the five-second connection wait and 30-second decision window. Web, plan-exit, MCP, persistent allow, and keystroke approvals stay native. The optional usage bridge is offered in the same preview and is off by default. Selecting it records the intent but does not edit `statusLine` until the compatibility probe passes; the core connection remains independent. The usage contract and proof boundary are documented in [Claude usage](claude-usage.md), and the bounded event payload, live question channel, and queue rules are documented in [Claude observations](claude-observations.md).

Question answers are fail-closed. Steer validates the installation, normalized Claude configuration root, separate event directory, session, prompt, tool-use, and fresh helper request identities, rechecks the helper-owned liveness marker immediately before writing, and spends the in-memory helper token before writing one answer. The helper emits a matching delivery acknowledgment only after Claude's response is written; a missing acknowledgment removes the unconfirmed answer and never reports it as sent. Expiry, malformed input, helper loss, uncertainty, or restart send no answer; Claude's native question remains authoritative when delivery is not confirmed. Multi-question calls and incomplete option lists stay in Claude.

The preview lists every affected `settings.json` field with its matcher, exact helper command, timeout, and owned environment value. It also lists the selected settings file, helper, event-record directory, install record, and backup directory. It does not display the complete `settings.json` or unrelated settings and credentials. Steer reads the root's session registry (`<CLAUDE_CONFIG_DIR>/sessions/<pid>.json`, one entry per live interactive Claude process) and falls back to `claude agents --json` in a bounded subprocess with the selected `CLAUDE_CONFIG_DIR` when the registry is absent or unusable; Claude Code 2.1.292 no longer accepts `--json`. Registry entries are raw process state: Claude rewrites them in place and leaves them behind after exit. An entry counts only while its PID is running (not a zombie) and, when Claude recorded `procStart`, that process started at the recorded UTC time, so a reused PID never revives a session. A torn entry is re-read a bounded number of times; one still torn from a live process makes the inventory unavailable, and one from an exited process is ignored. Only `interactive` entries (or entries without a `kind`, which Claude treats as interactive) become rows. Other holders of a session are not duplicates: a `bg` entry only marks its session as background, `daemon`, `daemon-worker`, and parked-job entries are skipped, and an unknown kind makes the inventory unavailable. The `shell` status, which Claude writes when the prompt is idle while a background Bash task keeps running, is read as `idle`. When both sources fail, the registry's failure is reported. Either source is bounded and then validated the same way: Steer validates the top-level array, canonical full session IDs, nonempty shared `cwd`/`name`/`startedAt` fields, supported kinds, lifecycle fields, and duplicate identities, then keeps only typed restart status for setup. The same typed snapshot is polled off the main actor for configured roots and contributes only generic lifecycle rows to the shared agent queue. Interactive status and background state are decoded independently; a background terminal state wins over a stale status. It never uses `cwd` or `name` as identity or targeting evidence. An active session counts as needing restart only when it started before installation and has no newly observed startup delivery; sessions started after installation or already observed by the exact startup hook are not counted. A disabled, failed, timed-out, malformed, incomplete, or duplicate inventory is reported as unavailable; Steer never treats it as an empty root, never persists the inventory payload, and does not clear stronger hook evidence.

Steer configures the selected user root. Claude can also merge project and command-line settings, and the supported CLI does not expose a per-key effective-settings resolver. Steer fails closed for a detected `CLAUDE_CONFIG_DIR` mismatch or managed policy. Project context is not supplied to this setup snapshot, so project and command-line `--settings` values remain unavailable in the preview. The UI warns that arbitrary future project files or command-line `--settings` values may override the selected root; Steer does not claim those values are absent or inspect the app's working directory as a substitute. It requires a new `SessionStart` event from the exact selected root before reporting Connected.

## States

- **Not configured**: no Steer install record exists for the selected root.
- **Configured; restart required**: owned files are present, but Steer has not observed a post-install startup event from this root.
- **Connected**: a newly received `SessionStart` event whose Claude `source` is `startup`, carrying this root's installation identity, was observed after installation. Resume, clear, compact, or other events from another root, another installation, another hook event, or before installation do not connect the root.
- **Repair required**: an owned hook or helper is missing.
- **Conflict**: an owned value changed, duplicate Steer installs exist, or the install record is inconsistent. Steer does not overwrite it.
- **Blocked by policy**: managed settings allow only managed hooks, or hooks are disabled.
- **Shadowed**: a higher-priority settings source wins; Steer does not try to defeat it.
- **Unsupported**: the detected Claude Code version is older than the tested `2.1.273` baseline. Newer versions still need a fresh runtime event before they become connected.

Ghostty readiness is separate from connection health. A root can be connected while Ghostty controls are off or still awaiting Automation permission. Exact return remains unavailable for stale, duplicate, overwritten, split, cross-window, or otherwise ambiguous targets.

## Exact Claude tab return (#84)

When Ghostty controls are enabled and permission is verified, Claude's **Open in Claude** action is
shown only for a canonical session that appears exactly once in every complete configured-root
inventory and in one current unsplit Ghostty tab titled `Steer Claude <full-session-id>`. The action
rechecks the root inventories, the complete Ghostty inventory, the exact window/tab/terminal
locator, and the selected front window before it can acknowledge queued outcomes. A title match
alone never acknowledges anything.

Manual acknowledgment requires a fresh Ghostty snapshot to observe the exact selected target change
after the outcome arrived. Since snapshots are polls, the outcome must also predate the prior
snapshot that establishes the transition lower bound; an outcome arriving between snapshots stays
queued. A tab that was already selected, a restored outcome with no new observed visit, an incomplete
inventory, or any uncertain target remains queued. The Open in Claude path has its own immediate
before and after selection checks and may acknowledge only after that verified selection.

Same-window return is supported. Duplicate live resumes, missing or stale sessions, overwritten
titles, split tabs, background Ghostty windows, failed inventories, and changed locators remain
unavailable without terminal input or acknowledgment. Ghostty Automation stays opt-in.
Background Claude sessions do not create separate queue rows or exact-tab warnings; only
interactive sessions can have a Ghostty target.

Automated coverage is in `Tests/SteerCoreTests/CLITests.swift`: canonical full-title matching,
duplicate and missing identities, overwritten and split titles, cross-window rejection before
selection, focus-transition timing, duplicate roots, and incomplete inventories. The focused and
full Swift suites cover source compatibility. Isolated live Claude/Ghostty return testing was
deferred by the operator and is not claimed here.

## Haiku session titles

Claude names a session it has not titled with a placeholder from its folder (`landbase-22`, registry `nameSource: "derived"`). This happens, for example, when a session opens with a slash command. The opt-in **Name sessions with Haiku** toggle on a ready root (off by default) lets the installed `UserPromptSubmit` hook replace that placeholder. The switch is the marker file `<events>/session-titles/enabled`; toggling it never edits `settings.json`.

The hook never waits on the model. On the session's first prompt that says something about the work (not empty, not a `<…>` message such as `<task-notification>`, not a bare slash command such as `/clear`), it records a pending attempt and starts itself detached as a generator. The generator receives the prompt's first 2,000 characters on stdin and runs one `claude -p --model haiku` call through the session's own Claude executable, with no tools, hooks, MCP servers, user or project settings, slash commands, or transcript. Its output goes to `/dev/null`, so Claude's wait for the hook ends when the hook exits. The generator writes a sanitized kebab-case title or records a failure. On any later prompt, the hook returns `hookSpecificOutput.sessionTitle` once, and Claude records the title with `nameSource: "hook"`. Steer's queue shows that registry name.

The hook reads `<CLAUDE_CONFIG_DIR>/sessions/<CLAUDE_PID>.json` and acts only while that entry belongs to the hook's exact session and still shows the derived name. A `/rename`, a `--name`, or Claude's own AI title always wins, and an unreadable or mismatched entry does nothing. A failed generation, or one still pending after two minutes, is retried on a later eligible prompt, with at most two attempts per session. A single-prompt session therefore keeps its placeholder. Records live in `<events>/session-titles/<session-id>.json`, hold only status, title, and attempt count, and are pruned after seven days. Titles are presentation only and are never identity or targeting evidence.

Automated coverage is in `Tests/SteerCoreTests/ClaudeSessionTitlesTests.swift`. A disposable interactive session in a scratch folder, run with the development `SteerHook` through `--settings` and a scratch events directory, did the following on Claude Code 2.1.295. The first prompt was answered while generation ran, and the title was ready about four seconds after the session started. The second prompt changed the registry from `work-02` (`derived`) to `move-rooms-booking-sheet-to-scheduler` (`hook`). A direct hook run returned in 52 ms with empty stdout, and its generator exited after writing the title.

## Ownership and undo

Reinstall reuses the root's installation identity and recreates only missing exact entries. Steer keeps the root's installed helper in step with the running app: at launch and on each setup refresh, when the bundled helper passes its self-test and differs from the installed copy, Steer replaces the helper and updates the helper recorded in `install.json`, only while the installed file is still exactly the one it recorded. This never reads or writes `settings.json`, so the connection state and undo snapshots are unchanged. Configure likewise replaces Steer's own unchanged helper with a newer bundled one instead of reporting a conflict. A helper that differs from the recorded one is never replaced and stays a conflict. Running hooks finish with the old helper; the next hook uses the new one. A changed owned handler or title environment value is a conflict. Undo restores the original `settings.json` byte-for-byte when it is unchanged; after unrelated edits it removes only unchanged Steer-owned entries and the exact title environment key, preserving other settings and environment formatting. Missing or inconsistent state refuses guessed restoration and leaves targeted manual recovery to the operator.

Automated coverage is in `Tests/SteerCoreTests/ClaudeSetupTests.swift`. It uses temporary roots only; it does not modify the user's Claude or Ghostty configuration. The sanitized isolated startup run record and commands are recorded in [Claude setup live evidence](evidence/claude-setup-live.md). The run record proves that a newly started disposable session delivered the exact-root hook events; existing sessions are intentionally reported as requiring restart. A helper self-test proves both title JSON shapes and the metadata boundary. Ghostty title application, clean SessionEnd reset, and the live old-session restart-required observation remain deferred operator checks; none is claimed as passed here. Those checks also do not prove that project and command-line settings were absent. Claude only delivers `SessionEnd` on supported clean shutdown paths, so reliable abrupt-exit title restoration remains unproven without a launcher or equivalent terminal lifecycle integration.
