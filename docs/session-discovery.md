# Session discovery — issue #44

Herdly shows Codex sessions that were already working before it launched, or before their first hook event reached it, instead of waiting for the next hook. Like [thread names](thread-names.md) and the [weekly limit](codex-usage.md), this rides on a private Codex format and fails soft: a session it cannot place is simply not shown as working, and discovery never creates a completion, request, question, or sound.

## What Codex records

Every rollout under `~/.codex/sessions/YYYY/MM/DD/rollout-<time>-<session id>.jsonl` opens with a `session_meta` line whose payload carries the session `id`, its `cwd`, and its `source`: `"cli"` for the terminal, `"vscode"` for the desktop app, `"exec"` for `codex exec`, and an object (`{"subagent":{"thread_spawn":…}}`) for a subagent thread. A turn begins with `{"type":"event_msg","payload":{"type":"task_started","turn_id":"…"}}` and ends with `task_complete` or `turn_aborted` for that `turn_id`. Every line written during the turn names it: event messages such as `item_completed` and `token_usage_record` carry `turn_id` in their payload, and response items carry it in `internal_chat_message_metadata_passthrough.turn_id`. A live turn keeps writing: a desktop thread that had been running for five hours while waiting on subagents was seen appending every minute. Observed with CLI 0.153.4 and desktop 26.901.51231.

## Herdly's rule

`SessionDiscovery.candidates` reads the 24 most recently modified rollouts from the newest day directories, skipping any not written within the last hour (`maximumAge`), any symlink, and any irregular file. For each it reads the first 64 KB for the `session_meta` line and the last 512 KB for turn events; a file smaller than that is read once. Only `cli` and `vscode` sessions are candidates: an `exec` run has no tab or thread to return to, and a subagent thread is Codex's own, not the user's.

`SessionDiscovery.open` takes the last turn any line names that no later `task_complete` or `turn_aborted` ended. This finds a long turn whose `task_started` line lies beyond the tail; its `startedAt` is then the earliest line seen for it, a lower bound on how long it has run, used only to order rows. A line written after an end seen in the same read (a trailing token count) does not reopen the turn; an end that itself fell just before the tail cut is not seen, so such a trailing line could name an ended turn until the next scan or the freshness bound clears it. A line that names no turn is skipped, including a partial line mid-append and the cut first line of a tail read.

`SessionDiscovery.running` decides which candidates are shown as working. A rollout alone never proves a session is alive, because a turn that died with its process leaves its start dangling:

- A desktop candidate needs the Codex desktop app running (`NSWorkspace`).
- A CLI candidate needs its session-ID title on a Ghostty tab right now (`GhosttyMatch.sessions`, when Ghostty controls are on and a snapshot is held) or, failing that, any Codex CLI process on this Mac (`CodexCLIProcesses` over the `ps -axo pid=,args=` listing, read from the kernel since #303: an executable named `codex`, `codex.js`, or `codex-…` that is not an `app-server`, which is the desktop app's own backend). The process check is per machine, not per session; the one-hour freshness bound limits what it can misattribute.
- A SessionEnd hook recorded after the turn started rules the session out whatever else is running.

A discovered session enters the queue through `AttentionQueue.apply(discovered:)`, keyed by session and turn like hook-derived work, so a later hook event for it merges into the same row and never duplicates it; when a hook has reported the session's running turn in the same scan, the hook's row stands. Completion evidence for its turn ends the row and the discovered turn cannot revive it. Discovered sessions get the thread name and Open in Codex target rules of any other session: a CLI session is added to the live set so its Ghostty tab can be matched, and a desktop session opens by its thread link. The process check is the one deliberate looseness: the issue asked for a live process for that session, which needs the session's open files (`lsof`) and a proof that Codex holds its rollout open; until then the machine-wide check plus the freshness bound stand in, and a CLI session that died within the hour while another runs would show as working.

## Subagent activity — issue #396

A subagent rollout is still never a session, but `CodexSubagentReader.activity` reads it to list what a working session's spawned agents are doing ([Subagent activity](../CONTEXT.md)). Recorded with desktop engine 0.164.0-alpha.11.1 (a root thread that spawned three research agents): the child's first line is a `session_meta` whose payload carries its own `id`, the root's `session_id`, `parent_thread_id` and `forked_from_id` naming its parent, a start `timestamp`, `thread_source: "subagent"`, `agent_nickname` (`"Kierkegaard"`), `agent_path` (`"/root/quiet_resorts"`), `subagent_history_start_ordinal`, and `source.subagent.thread_spawn` with `parent_thread_id`, `depth`, `agent_path`, `agent_nickname` and `agent_role` (null in every recorded child). The child then repeats its parent's header and history (the fork, which includes the parent's spawning turn, ended in the copy by `turn_aborted`), and its own history starts at that ordinal; every line carries an `ordinal`. The parent hands the task over as an `agent_message` whose plaintext reads `Message Type: NEW_TASK … Payload:` with the task itself in `encrypted_content`, and the child's tool calls are `custom_tool_call` `exec` scripts with `custom_tool_call_output` results.

The reader takes at most `ReminderReader.maximumChildProbes` (200) of the newest rollouts per scan from the same listing discovery uses, skips any not written within `maximumAge`, symlinks and irregular files, and reads each first line within 64 KB through `SessionDiscovery.read`. Only a header with a `thread_spawn` source and a parent by `CodexRolloutHeader.parent(in:)` is a subagent: the first of `parent_thread_id`, the spawn's `parent_thread_id` and `forked_from_id`, and none when two disagree (the rule `ReminderReader.rolloutParent` follows too). For subagents alone it reads the last 512 KB (the whole file when smaller), for at most `maximumTails` (24, discovery's file count) of them, newest written first; past that the scan stops.

Why this bound is acceptable: a scan reads at most 200 heads of 64 KB and 24 tails of 512 KB, about 25 MB, the same order as discovery's 24 heads and tails (about 14 MB). The worst case needs 200 rollouts written within the hour, and the running children of a session are the ones being written, so they come first. In practice a head read stops at the file's first line, files written within the hour are a handful, and a subagent's tail is the whole of a file of a few hundred KB. A smaller tail was not taken: one tool output over it leaves only a cut line, so the child would read as not running, the failure discovery already accepts at 512 KB. Lines before `subagent_history_start_ordinal` are the fork and are dropped; a repeated header must be the child's own, its parent's or the root's, or the child contributes nothing. The child is running while its own turn is open by `SessionDiscovery.openTurn`, the rule a session's turn follows; a turn that ended, or a rollout that is gone, drops the child from the next scan at once. A nested agent's parent chain is followed through the other subagent headers read, up to eight levels, and the agent is listed flat under the root session the chain reaches. When the chain stops at a parent that is not a root (the middle agent's rollout is missing, stale, or past the tail budget, judged by `thread_spawn.depth`), the agent falls back to the root its own header names as `session_id`. Two rollouts claiming one thread id are neither listed nor followed.

Each child becomes a `SubagentActivity`: `id` is its thread id; its name is `agent_nickname`, else the last component of `agent_path`, else "Subagent", numbered by `SubagentActivity.names` when two would read the same; `role` is `agent_role` when it is a non-empty string; `startedAt` is the header's `timestamp`; `asked` is the first message of the child's own history (a user-text message, a `user_message` event, or the handed-over task's plaintext payload), kept to 240 characters like a Claude prompt, and nil when that first message is unreadable, which is every recorded child, since the engine encrypts the task; the latest action is the newest call in the child's open turn that has no output yet, which is how the session's own "now" clears when its call completes. An `exec` script reads as its first `cmd` (`$ <command>`), any other call by its name, through `RunningRowDetails.now`. A header without a start time, an unparseable header, or a header still being written contributes nothing and never removes another child. The asked text can lie beyond the tail of a long-forked child and is then nil.

Each scan stores the result per root session, and `CodexAttentionAdapter.observations(…, subagents:)` gives each Codex working row its session's current list in `AgentRunning.subagents` (live only, not persisted). Measured on the inspected machine with a debug build: 1.5 ms per scan over the live `~/.codex/sessions` (no rollout written within the hour) and 11.7 ms per scan over copies of the three recorded children cut before their turn ends (three running agents, about 280 KB each), against 1.4 ms and 22 ms for `SessionDiscovery.candidates` over the same trees.

## App integration

Each two-second scan reads the candidates and the process list off the main actor alongside the hook events, rollouts, read state, names, and usage, then assembles `SessionLiveness` on the main actor from the desktop app's running state, the last Ghostty snapshot, and the scan's SessionEnd times. `--reminder-rollouts <path>` points a lab run at a copy of the sessions tree, as it does for reminders and usage. Restarts restore nothing here: discovery is re-derived from current evidence on every scan.
