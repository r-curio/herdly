# User-input requests

Steer surfaces a question Codex is asking the user (the desktop panel with a question, numbered options, a Skip button and a free-text field, or the equivalent CLI prompt) as a "Codex needs an answer" item in the notch, and clears it when Codex records the answer. It reads the question from the session rollout Steer already scans for turn completions, so it needs no new permission, hook, or app-server connection. Accessibility inspection of the Codex window remains rejected (see the [desktop investigation](codex-desktop-investigation.md)).

Accepted by the user on 2026-09-14 with a chime for fresh questions, a Dismiss control, and the session's "working" row withheld while it waits. Answering from the notch for CLI sessions in Ghostty was accepted the same day ([ADR 0006](adr/0006-relay-the-users-chosen-question-option-through-ghostty.md)); see "Answering from the notch" below.

## What Codex records

Codex asks through its `request_user_input` tool. The session rollout (`~/.codex/sessions/YYYY/MM/DD/rollout-<time>-<session>.jsonl`) records the call the moment the panel opens and the answer the moment the user submits it, as two `response_item` lines:

```
{"timestamp":"…T02:20:36.895Z","type":"response_item","payload":{"type":"function_call","name":"request_user_input",
  "call_id":"call_…","internal_chat_message_metadata_passthrough":{"turn_id":"<turn>"},
  "arguments":"{\"questions\":[{\"id\":\"…\",\"header\":\"Nested choices\",\"question\":\"Should different variant paths…?\",
                \"options\":[{\"label\":\"Flexible paths (Recommended)\",\"description\":\"…\"},{\"label\":\"Same levels throughout\",\"description\":\"…\"}]}]}"}}
{"timestamp":"…T02:21:41.908Z","type":"response_item","payload":{"type":"function_call_output","call_id":"call_…",
  "output":"{\"answers\":{\"…\":{\"answers\":[\"Flexible paths (Recommended)\"]}}}"}}
```

One call carries one or more questions (three is typical), and one turn can pose several calls in sequence, each answered before the next. A free-text answer appears as the answer string. The call carries the turn id in the same passthrough field the approval matcher already reads, and rollout turn ids equal the hook `turn_id` values in Steer's events directory. While the question waits, the turn is still running: the Stop hook fires only after the answer. Recorded from desktop 26.901.51231 (engine 0.153.4, `source` "vscode") in `docs/evidence/desktop-user-input-request.json`, with the option descriptions redacted.

Codex desktop also raises its per-thread unread flag when the request arrives (`item/tool/requestUserInput`), so the [desktop read state](desktop-read-state.md) shows the thread unread until it is viewed. Steer does not use that for questions; the rollout gives exact per-call evidence.

## Steer's rule

`ReminderReader.evidence` makes one pass over each scanned rollout (the same pass that finds ended turns) and collects every `function_call` named `request_user_input`. A question is:

- **Pending** while the file has no `function_call_output` for its call id. That is what the notch shows.
- **Answered** once an output for the call id exists. Any output counts; its content is not inspected, because Steer never needs to know the answer, only that Codex has one. No Skip or interrupt sample has been recorded yet; the walkthrough below records their shapes.
- **Ended** when the rollout records `task_complete` or `turn_aborted` for its turn, a desktop Stop hook completes the turn, or a SessionEnd hook arrives after the question. An ended turn also refuses a late question for that turn.

Identity is the session and call id, with the source (desktop or CLI) from the session's `session_meta`, like every other rollout-derived item; or, since the daemon, from Ghostty's tab titles (below). Fail-closed cases: a call without a call id (1 to 256 bytes), a UUID turn id, or a readable timestamp is not recorded, since Steer could neither clear nor open it; a rollout with any unreadable line yields no evidence at all, which the queue treats as "nothing new", never as an answer. Unreadable or oversize `arguments` (over 64 KB) still yield a question, shown without text, because the call itself is the evidence Codex is blocked. Display text is capped: eight questions, 80-character headers and option labels, 240-character questions, eight options; a capped prompt says so on the card. Option descriptions and the free-text field are never shown.

In the queue a question ranks after actionable approvals and ahead of handed-back requests: Codex is blocked on it and the user has not seen it, while a handed-back request was already surfaced once. Questions are rebuilt from rollout evidence on every scan and are not saved in the attention snapshot; a dismissal is in memory only, so a question still pending after a restart returns, without a chime. A session with a pending question has its "working" row withheld and its sprite standing still.

## Answering from the notch

Codex offers no way for another program to answer a question: the question tool provides no PreToolUse hook payload, the desktop engine is an embedded stdio app-server nothing can attach to, and the `codex://threads/<id>` link takes no parameters. Ghostty 1.3.1, however, scripts `send key` (a key event to one terminal object), and Codex's terminal question pane binds a digit to "select that option and move to the next question, or submit on the last" (`codex-rs/tui/src/bottom_pane/request_user_input/mod.rs`). So for a CLI session in Ghostty the card's options are controls, and a click relays one digit to that session's own tab. For a desktop session the options are a pick that opens the thread and stays highlighted on the card; nothing is sent.

The rule, in `QuestionAnswer.swift`, fails closed at every step:

1. A key is sent only after a click on an option button; never on a timer, retry, restart, or error.
2. Only the unique unsplit Ghostty terminal whose title equals the session's shortened id receives it, re-inventoried inside the same osascript call (`Ghostty.js`, action `answer`); any mismatch sends nothing. The window is not activated; the key goes to the terminal object.
3. Immediately before sending, the rollout is re-read (`ReminderReader.currentEvidence`); if it cannot be read, shows an output for the call, or shows the turn ended, nothing is sent (`QuestionAnswerGuard`).
4. One key per call and question index; a second press for the same question is refused (`QuestionAnswerPolicy`, which judges the queue's current copy of the question, never the rendered row).
5. Only `1` through `9` (and `enter`, if the live check below proves the digit alone does not commit) can leave Steer. No text, no Other, no Skip, no Escape.
6. Sending never dismisses the question; only rollout evidence or Dismiss clears it.
7. A sent last answer with no output within 10 seconds becomes "unconfirmed": the card says so and offers Open in Codex; Steer never resends.
8. Progress (`QuestionAnswerProgress`) is in memory only; after a restart the question is plain pending.
9. Ghostty disabled, desktop source, unreadable arguments, a typed answer, an option list Steer cannot number exactly (more than eight, or an unreadable label, `optionsComplete`), or a question beyond the eight parsed: no sending controls. `isOther` questions offer only the listed options; Codex's Other row is never sent.
10. Desktop: a pick is a highlight plus the deep link; no key or RPC is ever sent.

Because the rollout records nothing until the whole call is answered, a multi-question call is tracked optimistically: after a non-last digit the card says which question Codex should now be on and offers that question's options. Option positions are preserved when parsing, so a digit always names the option Codex lists at that position; a label Steer cannot read ends the list and takes the question back to Codex.

## Answering through the app-server daemon

Draft integration for issue #42, follow-up to ADR 0006; not a proven capability (see the evidence subsection below). Codex's app-server daemon (`codex app-server daemon start`) listens on `~/.codex/app-server-control/app-server-control.sock`, and the TUI attaches to it. A second JSON-RPC client subscribed to a thread receives `item/tool/requestUserInput` as a server request (`{threadId, turnId, itemId, questions[{id, header, question, options[{label, description}]?, isOther, isSecret}]}`) and may respond with `{answers: {<question id>: {answers: [<label or typed text>]}}}`; the other clients receive `serverRequest/resolved`. Shapes are from the installed CLI's generated schema (`codex app-server generate-json-schema`, 0.145.0). The thread id is the rollout's session id and the item id is taken to be the rollout's call id, so the request pairs with the queue's question by the identity Steer already uses.

Steer's daemon client (`AppServerDaemonClient`) starts nothing: every refresh it looks for the socket, connects only when the socket is a Unix socket owned by the user and private to them ([ADR 0007](adr/0007-connect-to-the-codex-daemon-socket-as-the-same-user.md)), sends `initialize` as `steer`, and every five seconds subscribes with `thread/resume` to each thread `thread/loaded/list` reports, never to one that is not already loaded. The controls window shows its state in one sentence.

The rule, in `AppServerQuestions.swift`, fails closed like the key relay:

1. A card uses the daemon path only while the connection holds the pending request for that exact thread and call id (`QuestionAnswerRouting`). Otherwise it is the pre-daemon card: the Ghostty key relay for a CLI session, the pick that opens Codex for a desktop one. Before anything is sent the card shows only the controls (the user asked for no explanatory sentence there); once something is sent, kept, refused or unconfirmed the status sentence names the path ("through Codex's daemon", "as a key to the Ghostty tab"). A waiting question on a thread Steer has not subscribed to triggers an immediate `thread/loaded/list`.
2. On the daemon path every option Codex lists is a control, whatever the count, and a question with no options or with `isOther` has a typed-answer field. A question marked `isSecret` offers nothing: the notch is not a private surface. The card shows the daemon's own text with the same display caps as the rollout prompt; the answer sent is the exact label or the trimmed typed text (at most 4,000 characters).
3. A multi-question call is answered in order: a non-last answer is kept in memory (`QuestionAnswerProgress.recordingDraft`) and the card moves to the next question; the last answer sends the whole call as one JSON-RPC response with every question id answered. Nothing is sent before the last answer.
4. Immediately before the response is written the rollout is re-read (`QuestionAnswerGuard`); an answer already recorded, an ended turn, or an unreadable rollout sends nothing.
5. One answer per call id, ever: the request is marked answered in the book before the write (`AppServerQuestionBook.markAnswered`), a failed write is final, a reconnect does not revive it, and the card refuses further clicks with "Steer already answered this question through Codex's daemon."
6. `serverRequest/resolved`, `turn/completed` and `thread/closed` drop the daemon's request (another client answered, or the pane is gone); losing the connection drops every pending request, since a request id belongs to its connection. None of that clears the queue item: only rollout evidence does, exactly as before, and a sent answer with no recorded output within ten seconds becomes unconfirmed, never resent.
7. Never on a timer, retry, restart, or error; nothing is answered in preview mode.
8. A desktop thread is answered the same way if the desktop app attaches to the daemon (the request then carries its thread id); otherwise the desktop pick is unchanged and the card says "No Codex daemon; a pick opens Codex". A pick made before the daemon delivered the request only opened Codex, so the daemon card then starts from its first question.
9. **Which surface a daemon session is.** A TUI attached to the daemon is recorded with `source: vscode` (the desktop's value) and an `originator` naming whichever client initialized the daemon first, observed on 0.154.0. So the rollout header no longer tells CLI from desktop, and Open in Codex would go to the desktop app. `ReminderReader.scan` therefore also treats a session as CLI when its session-id title (`GhosttyMatch.title`) is exactly one of Ghostty's current terminal titles, the titles Steer's own setup configures; the Companion passes the last Ghostty inventory into every scan. With Ghostty controls off there are no titles, and a daemon-attached TUI session shows as desktop until they are enabled. Exact match only: no prefix, cwd or substring matching (ADR 0005). Ghostty's inventory is read every two seconds whenever anything is queued or a CLI session is live, not only while a CLI completion waits. A session proved by title is remembered for the launch (`Companion.knownCLISessions`), so it stays CLI after its tab closes.
   **Closing the tab.** With the daemon, closing the Ghostty tab only disconnects the TUI: the thread stays loaded in the daemon and no SessionEnd hook fires, so the session would stay listed forever. A title-proved session whose title is absent from a later inventory is therefore ended by Steer, dated at that inventory: its running row goes, and a pending question or handed-back request clears as on any session end. A session the daemon has loaded whose rollout `originator` is not "Codex Desktop" is also CLI (the desktop app runs its own engine, so every daemon thread is a terminal session), which covers a session whose tab closed before Steer launched; such a session ends when an inventory taken at least fifteen seconds after its SessionStart shows no tab for it. A `source: cli` session in another terminal never ends this way; it still ends by its own hook. Unreadable Ghostty means no inventory and no ending. Separately, a running row now also ends on the rollout's own `task_complete` or `turn_aborted`, since a turn aborted as its tab closes writes no Stop hook.
10. The connection itself fails closed: a handshake not answered within ten seconds is dropped and retried five seconds later, a write waits at most half a second for the socket, and an oversized or closed stream disconnects. A dropped connection forgets its pending requests, never the calls Steer answered (those are forgotten only when their thread closes).

## Answering through herdr keys

Implemented for issue #126 per [ADR 0010](adr/0010-relay-codex-question-options-as-herdr-pane-keys.md); not a proven capability until the herdr live proof (#116, #128) records it. Pure rules are in `HerdrQuestionRelay.swift`; the send is `Companion.chooseOption` in `Companion+Questions.swift`.

1. **Route** (`QuestionRelayRouting`): a call Steer answered through the daemon stays there; a call that already carried a key keeps that key route (herdr or Ghostty) even if the daemon later holds it; otherwise the daemon wins when it holds the exact thread and call. A CLI session whose herdr binding is `bound` uses herdr keys, one whose binding is `unavailable` has no relay (`relayUnavailable`), and only a session not in herdr uses Ghostty keys, so no session is relayed through both. Answers drafted for a daemon that then loses the call are never continued by key.
2. **Eligibility:** the Ghostty relay's (`QuestionAnswerPolicy`, `QuestionAnswerProgress.offer`), with digits 1 to 8. A question marked `isSecret` in the rollout arguments offers nothing, on every key route.
3. **One key, spent first:** `QuestionRelayLedger` spends the key for the call and question index before anything is sent, and releases it only when herdr certainly received nothing. The request is one `agent.send_keys` with the digit alone, to the pane ID from the binding, never Enter.
4. **Fresh check, in this order:** a fresh scan (`revalidateHerdrBinding`), with fresh `pane.process_info`, must re-run [ADR 0012](adr/0012-bind-codex-herdr-panes-by-title-and-foreground-process.md)'s whole binding rule and still bind the same pane, and herdr must report its agent `blocked`; then the rollout is re-read and must show the call pending in its turn. Any failure sends nothing and yields one `HerdrQuestionRelayUnavailable` reason (exposed by `Companion.herdrRelayUnavailable(for:)` and listed under herdr diagnostics); the card keeps the generic wording and offers Open in Codex. When Open is unavailable too, the card instead shows one line, "Answer this in Codex." followed by Open's grouped reason (product.md, "Agreed herdr presentation").
5. **Delivery** (`HerdrKeyDelivery`): herdr `ok` means queued only. A timeout, disconnect, or malformed or mismatched reply once the write began counts as sent and is never resent; an explicit herdr error reply, or a failure before the write, is not sent. A non-last question then advances optimistically; the last waits for the rollout and becomes unconfirmed after ten seconds without output. Only resolution evidence or Dismiss clears the question.

## App integration

Each two-second scan carries pending and answered calls into `AttentionQueue.apply(scan:…)`. A fresh question (one recorded after Steer launched) opens its own card for three seconds under the same away-from-Codex rule as a completion and plays the completion sound once; a question already pending at launch is listed silently. The card shows the current question as Codex's own panel does (header, "1 of N", question, numbered option labels), a disclosure for the remaining questions, and Open in Codex and Dismiss. With Ghostty controls on, a CLI question's options are buttons (`Companion.chooseOption`); a CLI question with Ghostty controls off shows Set up Ghostty instead of Open in Codex. A desktop question's options are buttons that record the pick and open the thread. When the daemon holds the request, the card is the daemon card described above instead, with `Companion.answerText` for typed answers. A chosen option is drawn in the pressed look until Codex records the answer, and one status sentence names the phase: sending, sent and waiting, unconfirmed, refused, or the pick. Open in Codex returns to the session without dismissing. The badge counts the question. `--preview-queue expanded` includes a CLI sample with two questions and a desktop sample. The restart report lists question rows with their call id and, when Steer relayed something, the answer phase.
