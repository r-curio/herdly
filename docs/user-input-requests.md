# User-input requests

Herdly surfaces a question Codex is asking the user (the desktop panel with a question, numbered options, a Skip button and a free-text field, or the equivalent CLI prompt) as a "Codex needs an answer" item in the notch, and clears it when Codex records the answer. It reads the question from the session rollout Herdly already scans for turn completions, so it needs no new permission, hook, or app-server connection. Accessibility inspection of the Codex window remains rejected (see the [desktop investigation](codex-desktop-investigation.md)).

Accepted by the user on 2026-09-14 with a chime for fresh questions, a Dismiss control, and the session's "working" row withheld while it waits. Answering from the notch for CLI sessions in Ghostty was accepted the same day ([ADR 0006](adr/0006-relay-the-users-chosen-question-option-through-ghostty.md)); see "Answering from the notch" below.

## What Codex records

Codex asks through its `request_user_input` tool. The session rollout (`~/.codex/sessions/YYYY/MM/DD/rollout-<time>-<session>.jsonl`) records the call the moment the panel opens and the answer the moment the user submits it, as two `response_item` lines:

```
{"timestamp":"…T02:20:36.895Z","type":"response_item","payload":{"type":"function_call","name":"request_user_input",
  "call_id":"call_…","internal_chat_message_metadata_passthrough":{"turn_id":"<turn>"},
  "arguments":"{\"questions\":[{\"id\":\"…\",\"header\":\"Nested choices\",\"question\":\"Should different variant paths…?\",
                \"options\":[{\"label\":\"Flexible paths (Recommended)\",\"description\":\"…\"},{\"label\":\"Same levels throughout\",\"description\":\"…\"}]}]}"}}
{"timestamp":"…T02:21:41.908Z","type":"response_item","payload":{"type":"function_call_output","call_id":"call_…",
  "output":"{\"answers\":{\"…\":{\"answers\":[\"Flexible paths (Recommended)\"]}}}"}}
```

One call carries one or more questions (three is typical), and one turn can pose several calls in sequence, each answered before the next. A free-text answer appears as the answer string. The call carries the turn id in the same passthrough field the approval matcher already reads, and rollout turn ids equal the hook `turn_id` values in Herdly's events directory. While the question waits, the turn is still running: the Stop hook fires only after the answer. Recorded from desktop 26.901.51231 (engine 0.153.4, `source` "vscode") in `docs/evidence/desktop-user-input-request.json`, with the option descriptions redacted.

Codex desktop also raises its per-thread unread flag when the request arrives (`item/tool/requestUserInput`), so the [desktop read state](desktop-read-state.md) shows the thread unread until it is viewed. Herdly does not use that for questions; the rollout gives exact per-call evidence.

## Herdly's rule

`ReminderReader.evidence` makes one pass over each scanned rollout (the same pass that finds ended turns) and collects every `function_call` named `request_user_input`. A question is:

- **Pending** while the file has no `function_call_output` for its call id. That is what the notch shows.
- **Answered** once an output for the call id exists. Any output counts; its content is not inspected, because Herdly never needs to know the answer, only that Codex has one. No Skip or interrupt sample has been recorded yet; the walkthrough below records their shapes.
- **Ended** when the rollout records `task_complete` or `turn_aborted` for its turn, a desktop Stop hook completes the turn, or a SessionEnd hook arrives after the question. An ended turn also refuses a late question for that turn.

Identity is the session and call id, with the source (desktop or CLI) from the session's `session_meta`, like every other rollout-derived item; or, since the daemon, from Ghostty's tab titles (below). Fail-closed cases: a call without a call id (1 to 256 bytes), a UUID turn id, or a readable timestamp is not recorded, since Herdly could neither clear nor open it; a rollout with any unreadable line yields no evidence at all, which the queue treats as "nothing new", never as an answer. The one exception is a line over 1 MiB after the header (an image tool output, for example): it is skipped, and a question asked before it is treated as unknown, neither pending nor answered, so it is never answered from the notch. Unreadable or oversize `arguments` (over 64 KB) still yield a question, shown without text, because the call itself is the evidence Codex is blocked. Display text is capped: eight questions, 80-character headers and option labels, 240-character questions, eight options; a capped prompt says so on the card. Option descriptions and the free-text field are never shown.

In the queue a question ranks after actionable approvals and ahead of handed-back requests: Codex is blocked on it and the user has not seen it, while a handed-back request was already surfaced once. Questions are rebuilt from rollout evidence on every scan and are not saved in the attention snapshot; a dismissal is in memory only, so a question still pending after a restart returns, without a chime. A session with a pending question has its "working" row withheld and its sprite standing still.

## Answering from the notch

Codex offers no way for another program to answer a question: the question tool provides no PreToolUse hook payload, the desktop engine is an embedded stdio app-server nothing can attach to, and the `codex://threads/<id>` link takes no parameters. Ghostty 1.3.1, however, scripts `send key` (a key event to one terminal object), and Codex's terminal question pane binds a digit to "select that option and move to the next question, or submit on the last" (`codex-rs/tui/src/bottom_pane/request_user_input/mod.rs`). So for a CLI session in Ghostty the card's options are controls: a click or the option's digit selects it, and Send relays that one digit to that session's own tab (#321, D16). For a Codex app session the daemon does not hold, the options are for reading only: the card says "Herdly can't answer the Codex app. Answer it there." and offers Open in Codex and Dismiss; nothing is sent.

The rule, in `QuestionAnswer.swift`, fails closed at every step:

1. A key is sent only after Send for an option the user selected on the card (a click or its digit only selects); never on a timer, retry, restart, or error. One Send carries one key, for the question being answered only.
2. Only the unique unsplit Ghostty terminal whose title equals the session's shortened id receives it, re-inventoried inside the same script request (`Ghostty.js`, action `answer`); any mismatch sends nothing. The window is not activated; the key goes to the terminal object.
3. Immediately before sending, the rollout is re-read (`ReminderReader.currentEvidence`); if it cannot be read, shows an output for the call, shows the turn ended, or no longer shows the call as pending (a longer line after the call was skipped), nothing is sent (`QuestionAnswerGuard`).
4. One key per call and question index; a second press for the same question is refused (`QuestionAnswerPolicy`, which judges the queue's current copy of the question, never the rendered row).
5. Only `1` through `9` (and `enter`, if the live check below proves the digit alone does not commit) can leave Herdly. No text, no Other, no Skip, no Escape.
6. Sending never dismisses the question; only rollout evidence or Dismiss clears it.
7. A sent last answer with no output within 10 seconds becomes "unconfirmed": the card says so and offers Open in Codex; Herdly never resends.
8. Progress (`QuestionAnswerProgress`), selections included, is in memory only; after a restart the question is plain pending with nothing selected.
9. Ghostty disabled, desktop source, unreadable arguments, a typed answer, an option list Herdly cannot number exactly (more than eight, or an unreadable label, `optionsComplete`), or a question beyond the eight parsed: no sending controls. `isOther` questions offer only the listed options; Codex's Other row is never sent.
10. Codex app without the daemon: the options are read-only and nothing can be selected; no key or RPC is ever sent. Open in Codex opens the thread.
11. An earlier question's key that Herdly reports sent leaves the card open on the next question, its step review-only ("sent: 1 · <label>"), with "Typed 1 into this session's tab. Codex should now show question 2." ("pane" on a pane route), and the row notes "Sent 1 of 3, on question 2". A key that may have been written notes "Sent, not confirmed"; one not sent withdraws the note. The last question's key returns to the queue as before.

Because the rollout records nothing until the whole call is answered, a multi-question call is tracked optimistically: after a non-last digit the card says which question Codex should now be on and offers that question's options. Option positions are preserved when parsing, so a digit always names the option Codex lists at that position; a label Herdly cannot read ends the list and takes the question back to Codex.

## Answering through the app-server daemon

Draft integration for issue #42, follow-up to ADR 0006; not a proven capability (see the evidence subsection below). Codex's app-server daemon (`codex app-server daemon start`) listens on `~/.codex/app-server-control/app-server-control.sock`, and the TUI attaches to it. A second JSON-RPC client subscribed to a thread receives `item/tool/requestUserInput` as a server request (`{threadId, turnId, itemId, questions[{id, header, question, options[{label, description}]?, isOther, isSecret}]}`) and may respond with `{answers: {<question id>: {answers: [<label or typed text>]}}}`; the other clients receive `serverRequest/resolved`. Shapes are from the installed CLI's generated schema (`codex app-server generate-json-schema`, 0.145.0). The thread id is the rollout's session id and the item id is taken to be the rollout's call id, so the request pairs with the queue's question by the identity Herdly already uses.

Herdly's daemon client (`AppServerDaemonClient`) starts nothing: every refresh it looks for the socket, connects only when the socket is a Unix socket owned by the user and private to them ([ADR 0007](adr/0007-connect-to-the-codex-daemon-socket-as-the-same-user.md)), sends `initialize` as `herdly`, and every five seconds subscribes with `thread/resume` to each thread `thread/loaded/list` reports, never to one that is not already loaded. The controls window shows its state in one sentence.

The rule, in `AppServerQuestions.swift`, fails closed like the key relay:

1. A card uses the daemon path only while the connection holds the pending request for that exact thread and call id (`QuestionAnswerRouting`). Otherwise it is the pre-daemon card: the Ghostty key relay for a CLI session, read-only options for a Codex app one. Before anything is sent the card shows only the controls (the user asked for no explanatory sentence there); once something is sent, kept, refused or unconfirmed the status sentence names the path ("through Codex's daemon", "as a key to the Ghostty tab"). A waiting question on a thread Herdly has not subscribed to triggers an immediate `thread/loaded/list`.
2. On the daemon path every option Codex lists is a control, whatever the count, and a question with no options or with `isOther` has a typed-answer field. A question marked `isSecret` offers nothing: the notch is not a private surface. The card shows the daemon's own text with the same display caps as the rollout prompt; the answer sent is the exact label or the trimmed typed text (at most 4,000 characters).
3. A multi-question call is answered in order. Selecting an option, or typing in the field, sends nothing; Next keeps the answer in memory (`QuestionAnswerProgress.recordingDraft`) and the card moves to the next question; Send on the last question sends the whole call as one JSON-RPC response with every question id answered. Nothing is sent before that Send. An earlier step can be reopened and its draft changed before Send; later steps can be read but not answered out of order.
4. Immediately before the response is written the rollout is re-read (`QuestionAnswerGuard`); an answer already recorded, an ended turn, or an unreadable rollout sends nothing.
5. One answer per call id, ever: the request is marked answered in the book before the write (`AppServerQuestionBook.markAnswered`), a failed write is final, a reconnect does not revive it, and the card refuses further clicks with "Herdly already answered this question through Codex's daemon."
6. `serverRequest/resolved`, `turn/completed` and `thread/closed` drop the daemon's request (another client answered, or the pane is gone); losing the connection drops every pending request, since a request id belongs to its connection. None of that clears the queue item: only rollout evidence does, exactly as before, and a sent answer with no recorded output within ten seconds becomes unconfirmed, never resent.
7. Never on a timer, retry, restart, or error; nothing is answered in preview mode.
8. A desktop thread is answered the same way if the desktop app attaches to the daemon (the request then carries its thread id); otherwise its options are read-only and the card says "Herdly can't answer the Codex app. Answer it there." with Open in Codex and Dismiss (#321).
9. **Which surface a daemon session is.** A TUI attached to the daemon is recorded with `source: vscode` (the desktop's value) and an `originator` naming whichever client initialized the daemon first, observed on 0.154.0. So the rollout header no longer tells CLI from desktop, and Open in Codex would go to the desktop app. `ReminderReader.scan` therefore also treats a session as CLI when its session-id title (`GhosttyMatch.title`) is exactly one of Ghostty's current terminal titles, the titles Herdly's own setup configures; the Companion passes the last Ghostty inventory into every scan. With Ghostty controls off there are no titles, and a daemon-attached TUI session shows as desktop until they are enabled. Exact match only: no prefix, cwd or substring matching (ADR 0005). Ghostty's inventory is read every two seconds whenever anything is queued or a CLI session is live, not only while a CLI completion waits. A session proved by title is remembered for the launch (`Companion.knownCLISessions`), so it stays CLI after its tab closes.
   **Closing the tab.** With the daemon, closing the Ghostty tab only disconnects the TUI: the thread stays loaded in the daemon and no SessionEnd hook fires, so the session would stay listed forever. A title-proved session whose title is absent from a later inventory is therefore ended by Herdly, dated at that inventory: its running row goes, and a pending question or handed-back request clears as on any session end. A session the daemon has loaded whose rollout `originator` is not "Codex Desktop" is also CLI (the desktop app runs its own engine, so every daemon thread is a terminal session), which covers a session whose tab closed before Herdly launched. That proof is remembered for the launch (`Companion.rememberedDaemonCLISessions`), because the loaded list is empty before the first poll and after every daemon disconnect, and dropped once a list polled on a live connection lacks the session (#359); the memory only classifies, so a remembered session the daemon no longer lists is never ended for lacking a tab. A session the daemon lists ends when an inventory taken at least fifteen seconds after its SessionStart shows no tab for it. A `source: cli` session (`codex --no-daemon`) ends by its own hook, and also, since a tab closed under it kills it before that hook runs (#285, decided 2026-10-15), when no tab shows its title and either the switched-on host that last showed it reads without it, or Ghostty proved it and a Ghostty inventory no longer shows it. One never seen in a readable host still ends only by its own hook. Live, 2026-10-15 (build 482 of `fix/285-direct-cli-tab-closed`, 44e8263): a `--no-daemon` session in WezTerm with a queued completion, tab closed with `wezterm cli kill-pane`, read "Open Session unavailable. This session has ended." Unreadable Ghostty means no inventory and no ending. Separately, a running row now also ends on the rollout's own `task_complete` or `turn_aborted`, since a turn aborted as its tab closes writes no Stop hook.

   **Every terminal host (#265).** Codex 0.162.1 runs every CLI thread in the daemon (`source: vscode`, originator `herdly`) wherever its TUI runs, so "no tab shows it" counts every host, not only Ghostty and herdr (`ReminderReader.scan`, `TerminalHostTitles`). The titles come from the inventories that the iTerm2, Terminal.app, WezTerm, tmux and Zellij scans already read; the newest reading per host wins, whatever order scans finish in, and a host Herdly may no longer contact is forgotten. The rule, per session that no tab shows:
   - **Live surface.** Its title on any tab or pane of a switched-on host keeps it live, exactly as a Ghostty tab title or herdr pane title does, and records that host as where it was last seen.
   - **Where the check runs.** While Ghostty is switched on, only with a readable Ghostty inventory (Ghostty unreadable or not running ends nothing, as before). While Ghostty is switched off, on the switched-on hosts' inventories alone, so closing an iTerm2 tab ends its session (MVP acceptance H7). The end is dated at the newest inventory consulted.
   - **Proved by a Ghostty title.** Once no switched-on host shows its title, it ends when its Ghostty tab closes, even while another host is unread or a host Herdly cannot read holds a Codex TUI: a tab cannot move between apps. Herdr's unknown titles still hold it back, as before, and so does a terminal app that last showed it and is not running (below).
   - **Known only from the daemon.** It ends only when every switched-on host's inventory is readable and taken at least fifteen seconds after its SessionStart. While one is unread, unreadable or older, the iTerm2, Terminal.app and WezTerm scans read even when they have nothing of their own to show, so the check is not held back indefinitely. They also re-read when such a session is shown only in readings at least fifteen seconds older than the newest inventory, since its tab may have closed after the host was last read.
   - **A host Herdly cannot read.** A switched-off host (Ghostty included) is never scanned or contacted, and neither is a tmux or Zellij server other than the default one. Herdly walks the process ancestry of each running Codex TUI, from the process list it already reads (`CodexCLIProcesses.hostReached`: the nearest tmux, Zellij or herdr server, otherwise the nearest app). A switched-off app or multiplexer that a Codex TUI reaches is unseen; so is a switched-on tmux or Zellij when more Codex TUIs run under its servers than its default server's reading shows Codex titles (or its default server is not running), since some run on a server Herdly does not read. While a host is unseen, a session known only from the daemon is not ended: product.md says a Codex session in a switched-off app cannot have its app identified, so Open shows "Herdly can't tell which terminal this session is in." (H8). With no Codex TUI under it, a switched-off app or server is irrelevant even while it runs, and a session whose tab closed while Herdly was down ends as above. An unreadable process list counts as reaching every host. A Codex TUI under herdr never makes a host unseen: herdr is governed only by its own pane titles, which carry no timestamp, unchanged from before.
   - **Its app not running.** A switched-on terminal app that is not running holds no tab, but a session whose title that app last showed is not ended while it is down: Open shows "<app> isn't running." first, and the session ends only after the app is relaunched and its tab is gone (H7). A stopped tmux or Zellij server holds nothing: its panes are gone, so a session last seen there ends as above.

   Automated: `Tests/HerdlyCoreTests/CodexSurfaceHostTests.swift`.

   **herdr panes and resumes (ADR 0012, 2026-10-08).** A session whose title is on a pane in the latest successful herdr snapshot is also CLI with a live surface: that pane is its surface, so it is not ended for lacking a Ghostty tab (its own SessionEnd hook still ends it), and it is not remembered as Ghostty-titled. While herdr may be in use but its pane titles are unknown (before its first scan, or after a failed one, while the gate is open or herdr's default socket passes the trust check), no session is ended for lacking a Ghostty tab; a herdr server that is not running shows no title, so it does not hold this back. The fifteen-second grace is timed from the session's latest SessionStart, and a session that ended and later started again (`codex resume`, or the TUI reopening a thread) is live again; its last end is still kept for resolving requests received before it.
10. The connection itself fails closed: a handshake not answered within ten seconds is dropped and retried five seconds later, a write waits at most half a second for the socket, and an oversized or closed stream disconnects. A dropped connection forgets its pending requests, never the calls Herdly answered (those are forgotten only when their thread closes).

Automated: `Tests/HerdlyCoreTests/AppServerQuestionTests.swift` covers parsing by thread, item and question id, malformed requests, every resolution event, routing, the policy table (not in queue, no request, already answered, wrong question, option out of range, text where options are required, empty and oversize text, secret, every non-ready phase), the response shape, exactly one answer per call id with a fake client, refusal on rollout uncertainty and after another client resolved the request, the single-question call, and the socket check. `python3 scripts/daemon_lab.py --herdly .build/debug/Herdly` drives the real binary against a fake daemon on a scratch socket (connect, initialize as `herdly`, subscribe, receive the request, the card routed to the daemon, nothing answered), and proves a world-readable socket is refused and a missing one reported; results in `docs/evidence/app-server-daemon-lab.json`. `--daemon-socket <path>` and `--daemon-report <path>` exist for that lab only.

Probe: `python3 scripts/probe_app_server_daemon.py --status | --handshake | --watch [--record FILE]` is the read-only client for the live proof; `--watch --answer ITEM_ID --with QUESTION_ID=TEXT` is its one writing mode, for a person.

Live proof, for a person, with `python3 scripts/probe_user_input.py --watch` beside the notch:

1. Decide whether a daemon belongs in your workflow: `codex app-server daemon start` on this machine refuses without the managed standalone install (`docs/evidence/app-server-daemon.json`). If you install it, record which Codex the TUI now runs and whether the daemon starts on its own.
2. With the daemon running and a TUI session open, run `--status` (socket present, owned by you, mode 0600 or 0700) and `--handshake` (initialize succeeds; `thread/loaded/list` includes the TUI's session id). Record both outputs under `docs/evidence/`.
3. Run `--watch --record docs/evidence/app-server-daemon-watch.jsonl`, then in the TUI ask "Use request_user_input to ask me one multiple-choice question with two options." This is the proof that a second client receives the request.
4. Repeat, and answer from the probe with `--answer <itemId> --with <question id>=<label>`. Expect the TUI to continue and the rollout output to record that label. Then repeat with a typed answer.

7. Stop the daemon with the card open. Expect the card to fall back to the Ghostty path ("No Codex daemon; an option goes to the Ghostty tab as its key") and the controls window to say the daemon is not running. Also start Herdly after the question is already open: record whether `thread/resume` delivers the pending request (the card goes to the daemon path) or not (the card says "Codex's daemon does not hold this question").
8. Desktop: with the daemon running, open a desktop thread and ask a question. Record whether `thread/loaded/list` on the daemon lists it; if not, the desktop card must say "Herdly can't answer the Codex app. Answer it there." with read-only options.

## Answering on other terminal hosts

Decided on 2026-10-11 in [ADR 0017](adr/0017-type-question-digits-and-replies-into-one-bound-pane.md): the same one-digit relay extends to WezTerm, tmux and Zellij panes, each only after a live run shows the digit alone commits there. Built for WezTerm (#240) and switched off: `TerminalQuestionKeys` (host-neutral: the digit spent on the clicked pane before the send, then a fresh binding naming that same pane and a fresh rollout read showing the call pending, never Enter, never resent) and WezTerm's `send-text --no-paste` carry it as the route `terminalRelay`, offered only for a host whose `typesQuestionDigits` is on. WezTerm's is `WezTermInput.questionDigitsProvenLive`, false until its acceptance (#245) shows the digit alone commits; until then a Codex question whose title a WezTerm pane carries shows "Answer this in Codex." (`relayUnavailable(.noQuestionKeys(.wezTerm))`). tmux is built (#241) and switched on since its acceptance (#246, 2026-10-25), after a lone digit committed a Codex answer: `TmuxInput.questionDigitsProvenLive` is true; its digit is one `send-keys -t %pane -l -- <digit>` through the same `terminalRelay`, with a fresh check that also requires the pane out of copy mode, not nested and shown by no control-mode client, sent only to the server that check read. Zellij is built (#242) and switched on since its acceptance (#247, 2026-10-25), after a lone digit committed a Codex answer and Herdly's own route recorded the option picked on the card: `ZellijInput.questionDigitsProvenLive` is true; its digit is one `write-chars --pane-id terminal_<n> -- <digit>` through the same `terminalRelay`, with a fresh check that also requires Zellij's pane layer, sent only after the pane is re-read under the server that check read. Terminal.app and iTerm2 get no question keys. Built for Terminal.app (#239): when the daemon does not hold the call and the latest scan saw the Codex session's title in a Terminal.app tab, `QuestionRelayRouting` returns `relayUnavailable(.noQuestionKeys(.terminalApp))` and the card says "Answer this in Codex." with Open. This applies to a session bound in herdr too: a herdr key also needs the title unique across the enabled hosts, so herdr keys are withheld while another host holds the title or is unreadable (a conservative choice pending a product decision, since ADR 0017 says a multiplexer send needs only the pane layer). A session any other host holds is never relayed to Ghostty. While another terminal host's switch is on, Ghostty keys fail closed: the card offers none while that host's latest read is missing, unreadable or denied, and the send reads it fresh immediately before the key, sending nothing if it is unreadable or one of its tabs carries the session's title (`TerminalKeyRelayCheck`). Claude questions are never typed.

## Answering through herdr keys

Implemented for issue #126 per [ADR 0010](adr/0010-relay-codex-question-options-as-herdr-pane-keys.md); not a proven capability until the herdr live proof (#116, #128) records it. Pure rules are in `HerdrQuestionRelay.swift`; the send is `Companion.chooseOption` in `Companion+Questions.swift`.

1. **Route** (`QuestionRelayRouting`): a call Herdly answered through the daemon stays there; a call that already carried a key keeps that key route (herdr or Ghostty) even if the daemon later holds it; otherwise the daemon wins when it holds the exact thread and call. A CLI session whose herdr binding is `bound` uses herdr keys, one whose binding is `unavailable` has no relay (`relayUnavailable`), and only a session not in herdr uses Ghostty keys, so no session is relayed through both. Answers drafted for a daemon that then loses the call are never continued by key.
2. **Eligibility:** the Ghostty relay's (`QuestionAnswerPolicy`, `QuestionAnswerProgress.offer`), with digits 1 to 8. A question marked `isSecret` in the rollout arguments offers nothing, on every key route.
3. **One key, spent first:** `QuestionRelayLedger` spends the key for the call and question index before anything is sent, and releases it only when herdr certainly received nothing. The request is one `agent.send_keys` with the digit alone, to the pane ID from the binding, never Enter.
4. **Fresh check, in this order:** a fresh scan (`revalidateHerdrBinding`), with fresh `pane.process_info`, must re-run [ADR 0012](adr/0012-bind-codex-herdr-panes-by-title-and-foreground-process.md)'s whole binding rule and still bind the same pane, and herdr must report its agent `blocked`; then the rollout is re-read and must show the call pending in its turn. Any failure sends nothing and yields one `HerdrQuestionRelayUnavailable` reason (exposed by `Companion.herdrRelayUnavailable(for:)` and listed under herdr diagnostics); the card keeps the generic wording and offers Open in Codex. When Open is unavailable too, the card instead shows one line, "Answer this in Codex." followed by Open's grouped reason (product.md, "Agreed terminal host presentation").
5. **Delivery** (`HerdrKeyDelivery`): herdr `ok` means queued only. A timeout, disconnect, or malformed or mismatched reply once the write began counts as sent and is never resent; an explicit herdr error reply, or a failure before the write, is not sent. A non-last question then advances optimistically; the last waits for the rollout and becomes unconfirmed after ten seconds without output. Only resolution evidence or Dismiss clears the question.

## App integration

Each two-second scan carries pending and answered calls into `AttentionQueue.apply(scan:…)`. Fresh questions retain their existing spotlight, sound, ordering, resolution, and dismissal rules. The 2026-10-16 [Paper redesign](https://app.paper.design/file/01M51985RZGVMFW23BNQWAFNY5/p-1-0) applies to Codex and Claude cards in both spotlight and queue; visual details are in [DESIGN.md](../DESIGN.md#question-cards--paper-redesign).

The rail, the clicked card's "‹ question N of M ›" stepper, and a reviewed step's "<next step> ›" button change only the viewed question. The viewed index is separate from the answering position and scoped to source, session, turn, call, and helper/daemon request identity. Navigation sends nothing. Future questions can be read but cannot be answered out of order. Earlier terminal-key answers remain review-only, with the selected answer retained, no text field, and no key resend. Codex app questions without the daemon are read-only. Unsupported Claude multi-question requests are browsable references; a single Claude question is answered by selecting (ticking, for multi-select) or by typing in its "Or type an answer" field, then Send, which stays disabled until something is selected or typed (`ClaudeQuestionSelection`); typing clears a selected option and selecting clears the text, so one Send carries exactly one answer, and each keeps its existing live-helper checks.

Select, then Send (#321, D16): a click on an option or its digit (1 through 9, while the card is shown) only selects it (`QuestionAnswerProgress.selecting`); Return does the card's Next or Send while it is enabled (`QuestionCardPrimary`). Nothing leaves Herdly until Send, and each Send keeps its route's fresh pending-request check.

A daemon's earlier draft can be changed only while that exact request remains pending and ready. Replacement preserves other drafts and the next unanswered position and clears the previous answer kind (option versus text). It sends nothing, so it reads no rollout; the final Send's fresh check covers every draft. The final explicit answer still submits the entire call once, after the existing fresh check; navigation, timers, errors, and disconnects never submit. Once sending starts, answers cannot be edited. An earlier step's typed text becomes its draft only on Return; leaving that step discards unsubmitted text, so the step shows its draft again and no step shows text that Send would not send (`QuestionTypedDrafts`). A replacement daemon request does not inherit drafts or typed text from the old request. Typed text rejected before acceptance stays available to edit. View navigation and text drafts are transient and pruned when their matching request disappears.

Open Session returns to the source without dismissing; Dismiss only clears the card. All existing unavailable/setup actions and uncertain-delivery messages remain. The reference's transport-specific states do not enable any previously disabled transport.

Preview modes (in-memory fixtures, no real sends): `spotlight-question` shows question 2 with question 1 drafted; `spotlight-question-edit` reviews that editable draft; `spotlight-question-review` reviews a spent Ghostty answer; `spotlight-question-long` and `spotlight-question-unavailable` cover long text and failure; `spotlight-claude-question` is read-only and `spotlight-claude-multiselect` exercises selection controls. `expanded` includes multiple card types. `--preview-width standard|wide|extraWide` changes preview appearance only. The three Paper states use the same package/payment sample text as the reference.
