# Replying to a session from its completion card

A CLI completion card carries a single-line field: the user reads that a session finished, types "now add tests", and sends it to that session without switching applications. The reply starts a new turn on that exact thread through the local app-server daemon, the same verified transport that answers questions by call id ([user-input requests](user-input-requests.md), [ADR 0007](adr/0007-connect-to-the-codex-daemon-socket-as-the-same-user.md)). Desktop completion cards omit the reply field and Send because Herdly has no supported desktop reply transport. Open and Dismiss remain available. The field lives on the result card (the spotlight, #323); since #322 a result row in the open queue is one line with Dismiss and no reply field, and clicking it opens the session.

## The only transport

`turn/start` on the daemon socket carries the reply:

```
{"jsonrpc":"2.0","id":7,"method":"turn/start",
 "params":{"threadId":"01a09d9b-…","input":[{"type":"text","text":"now add tests"}]}}
```

Params and shapes follow the schema the installed CLI generates (`codex app-server generate-json-schema --out <dir>`, 0.154.0): `TurnStartParams` requires `threadId` and `input`, and every other field is an override of the thread's model, effort, sandbox policy, approval policy, working directory or service tier. Herdly sends none of them, so the reply inherits exactly the settings the session already has.

The socket itself is proven: a second client connects, subscribes and receives a real `item/tool/requestUserInput` ([ADR 0007](adr/0007-connect-to-the-codex-daemon-socket-as-the-same-user.md); raw lab record not kept in the repo). `turn/start` has been run live too: in the iTerm2 acceptance run (build 456), the card's reply "kilo" reached Codex through the daemon and started a turn ([iTerm2 acceptance](evidence/iterm2-acceptance.md), H9 Codex reply).

The Ghostty relay is not a second path. It delivers one key name to a matched tab and was verified for that alone (ADR 0006); nothing proves it can type a whole prompt and a Return into one unsplit tab, so a session the daemon does not hold has no reply path in Herdly at all. Amended on 2026-10-11 by [ADR 0017](adr/0017-type-question-digits-and-replies-into-one-bound-pane.md): typing the reply into the session's one bound pane is a second path, used only when the daemon does not hold the thread, on the hosts that ADR lists. It is built for Terminal.app (#239, below), WezTerm (#240, below), tmux (#241, below) and Zellij (#242, below), and is the only reply path for Claude Code sessions. `turn/steer`, which interjects into a running turn, is not used either: a completion card is about a turn that has ended.

## Typed into the bound tab (#239)

[ADR 0017](adr/0017-type-question-digits-and-replies-into-one-bound-pane.md)'s second route is built host-neutrally in `Sources/HerdlyCore/TerminalTypedInput.swift`; Terminal.app is its first host. Other hosts reuse it when their tickets set `TerminalHost.typesReplies` and supply their send.

- **Route:** each scan turns the session's tab binding (ADR 0013) into a `TerminalReplyRoute`: `pane` for the exact binding on a host that types replies, `unreachable` for no exact binding ("Herdly can't reach this session's tab. Reply in the session."), `hostCannotType(.iTerm2)` ("Herdly can't type into iTerm2. Reply in the session."), or none, which leaves the daemon's reasons below. `SessionReplyRouting.target` checks ended, then working, then the daemon (which wins whenever it holds the thread), then the typed route. An Open fallback is never an input target.
- **Text:** trimmed, 1 to 4000 characters, one line without control characters, never starting with `/` or `!` (`TypedReplyText`). The daemon route keeps its existing rules.
- **Writes:** Claude gets text and submit in one write; Codex gets the text, then a separate submit one second later (`TypedReplyWrites`). On Terminal.app each write is one `do script … in <tab>`, which appends the newline itself, so Codex's submit is an empty `do script` (`TerminalAppInput`).
- **Fresh check before every write** (`TypedReplyCheck`): the completion still queued and the session's latest; the session idle (Codex: not in a turn and the rollout shows the turn ended; Claude: a fresh interactive inventory reads idle); no pending question or approval; the daemon not holding the thread; and the binding re-run on fresh reads (two Terminal.app inventories and `ps -t`) naming the same tab. Any veto before the first write sends nothing. The card then refuses another send, including when the daemon took over the thread after the click ("Codex's daemon now holds this session; nothing was sent. Reply in Codex."). That is the current conservative choice, applying "one card sends at most one reply" to a send that started; whether a card whose send sent nothing may send again is an open product decision, not agreed behavior.
- **Sent:** `TypedReplySequence` sends each write at most once. A write that may have reached the tab counts as sent and is never resent. If Codex's text went in but its submit was vetoed or not written, the card says the text may be waiting in Codex's composer, and Herdly never presses Return later. Confirmation is a turn started after the send (below). If none is seen within ten seconds the card says "Check the session; Herdly will not resend.", and a turn start found later still confirms it.
- **Claude cards** show the field only while a host that types replies is on and the session's route is one exact pane (`ClaudeReplyRouting`, `ResultCardReply.offersField`), with the same one-reply rules.

Automated: `TerminalTypedInputTests` (hosts and routes, the daemon winning, text rules, write plans, Terminal.app delivery, every fresh-check veto, the check before every write, the one-second submit, no resend, the composer case, Claude routing) and `TerminalAppTests`. Live application proof: [Terminal.app acceptance](evidence/terminal-app-acceptance.md) (#244, build 473), H9: a Codex reply and a Claude reply typed from the cards each landed in their own window only and each session answered; the cards' wording after sending was not recorded.

### WezTerm (#240)

WezTerm is the route's second host (`TerminalHost.wezTerm.typesReplies`); its switch is shown since #245. Each write is one `wezterm cli --no-auto-start send-text --no-paste --pane-id <id> -- <payload>` (`WezTermInput`): Claude's payload is the text and a CR, Codex's is the text, then a CR alone one second later, as the live proof required. `--` keeps text starting with `-` from being read as an option. The fresh check before every write re-runs the binding on fresh reads of every enabled host (WezTerm read twice with `ps -t` between). A send that exited 0 is written; nothing run (no binary, no trusted socket) or WezTerm's "no such pane" is not written; any other error or a timeout may have typed and counts as sent. Terminal.app's and WezTerm's latest scans each give a route, merged so that anything other than one exact pane wins (`TerminalReplyRoute.merging`). Automated: `WezTermTests`. Live application proof: #245's acceptance run on build 484 ([evidence](evidence/wezterm-acceptance.md), H9): a Claude reply and a Codex reply typed from the cards landed only in their bound panes and committed.

### tmux (#241)

tmux is the route's third host (`TerminalHost.tmux.typesReplies`), shown since its acceptance run (#246). Each write is one `tmux -S <default socket> -N send-keys -t %<pane> …` (`TmuxInput.arguments`): text as `-l -- <text>`, Claude's text and CR together as `-l -- <text>\r`, and Codex's submit as a separate `Enter` one second after its text, as the live proof required. The fresh check before every write re-runs the binding on fresh reads of every enabled host, tmux read twice with `ps -t` between, and requires the pane layer (not nested in tmux, herdr or Zellij) with `pane_in_mode` 0, a live pane and input on (`TmuxInput.route`), so a pane in copy mode is unreachable and nothing is typed there. A session shown by a control-mode client (iTerm2's `-CC`) is unreachable too, the current conservative choice pending a product decision. A text whose last character is `;` is sent with it escaped as `\;`, since tmux would otherwise drop it as a command separator (`TmuxInput.literal`). Each write goes only to the tmux server the fresh check read (`TmuxRunner.send`): a restarted server gets nothing. A send that exited 0 is written; a non-zero exit (tmux refusing before it wrote, such as "can't find pane") or a binary that would not start is not written; a send that did not return within two seconds counts as sent (ADR 0017). tmux's latest scan route is merged with the other hosts' (`TerminalReplyRoute.merging`); an unreadable tmux makes every route unreachable. Automated: `TmuxTests`. Live application proof: [tmux acceptance](evidence/tmux-acceptance.md) (#246), H9: Codex and Claude replies typed through the cards landed only in their own panes and committed, with the tmux client inside WezTerm, iTerm2 and Terminal.app.

### Zellij (#242)

Zellij is the route's fourth host (`TerminalHost.zellij.typesReplies`), shown since its acceptance run (#247). Each write is one `zellij --session <name> action …` (`ZellijInput.arguments`): text as `write-chars --pane-id terminal_<n> -- <text>`, Claude's text and CR together in one `write-chars`, and Codex's submit as a separate `write --pane-id terminal_<n> 13` one second after its text, as the live proof required. The fresh check before every write re-runs the binding on fresh reads of every enabled host (Zellij's pane by ADR 0014's Codex or Claude rule, `ZellijInput.route`) and requires the pane layer (alone and tiled in its tab, not exited, no client nested in another multiplexer). Because `write-chars` to an unknown pane exits 0 having written nothing, each write is sent only after a read taken immediately before it shows the bound pane still a live, single terminal pane of its session under the server identity the fresh check read (`ZellijRunner.send`, `ZellijInput.writeAllowed`); otherwise nothing is written. A write that exited 0 is written; a non-zero exit or a binary that would not start is not written; a write that did not return within two seconds counts as sent (ADR 0017). Zellij's latest scan route is merged with the other hosts' (`TerminalReplyRoute.merging`), and the other hosts leave a session Zellij holds to Zellij's route; an unreadable Zellij makes every route unreachable. Automated: `ZellijTests`. Live application proof: [Zellij acceptance](evidence/zellij-acceptance.md) (#247), H9: replies typed through the card landed only in their own pane, Codex's in WezTerm, iTerm2 and Terminal.app and Claude's in WezTerm.

## When the field is offered

For CLI cards, `SessionReplyRouting.target` reads what Herdly can see at that instant, in this order. Since #323 the card shows the field only for a reachable target while it has sent nothing (`ResultCardReply.offersField`); every other row has no field and no reason line, and the card offers Open and Dismiss. The sentences are still what a refused send is judged by (`SessionReplyPolicy.message`).

| Evidence | Card |
| --- | --- |
| Codex recorded the session's end | no field ("This session has ended; there is nothing to reply to.") |
| The session is in a turn | no field ("This session is working again; send your next prompt in Codex.") |
| No daemon connection, and no typed route | no field ("No Codex daemon is running, so Herdly cannot reach this session; reply in Codex.") |
| The daemon does not list the thread as loaded, and no typed route | no field ("Codex's daemon is not holding this session; reply in Codex.") |
| A typed route without one exact pane, or iTerm2 | no field ("Herdly can't reach this session's tab. Reply in the session." / "Herdly can't type into iTerm2. Reply in the session.") |
| The daemon holds the thread, or a typed route names one exact pane | the field is live; Send appears in it once there is text |

A Codex app result has no field even when the daemon holds its thread. A Claude result shows the field only with a typed route to one exact pane while the session is idle.

An ended session has nowhere to put a turn; a session that started another turn is an ambiguous target, because a `turn/start` against it is not the interjection the user is imagining (`turn/steer`, which does interject, is a different method with an `expectedTurnId` precondition and is not used here). Both are told plainly rather than attempted.

"In a turn" is read from `AttentionQueue.sessionsInTurn`, not from the rows on screen: a session blocked on a question has its running row withheld from the display but is mid-turn all the same, and a reply to it would be exactly the ambiguous send this rule exists to refuse.

## One card, one reply

Enter in the field or the Send button sends once. The policy is re-applied against the queue's current copy of the completion and the target as they are at that moment, never the row that was rendered, and the text is trimmed, non-empty and at most 4000 characters. A refused send (a session that started another turn, text the route refuses) sends nothing, keeps the card and its text, and leaves no note. A send that leaves `.ready` folds the card at once (`ResultCardReply.foldsCard`, #323): the spotlight collapses as Escape's does, nothing is dismissed, and from then on the result row in the open queue carries the reply's progress as its row note, in place of its place label (`RowNote.reply`). The reply follows one path only:

- **sending** — the request is in flight. Row note: "Sending…".
- **sent** — the daemon accepted it, or the text and its submit were typed. Row note: "Sent, waiting for Codex" ("Sent, not confirmed" for a Claude reply, and for Codex text whose submit was not written, which may be waiting in the composer).
- **working** — Codex started a turn on the session after the send, and a late turn still counts. The evidence is either the session seen in a turn, or a `UserPromptSubmit` record for the session dated at or after the second the send began (`ReplyTurnStarts`, `ReplyProgress.observing`). The record matters for a turn that starts and finishes between two scans, which no scan ever sees running (#271); it is read both from the CLI events and from the hook reader that decodes every record, so a session the scan did not classify as CLI this time still confirms. Hook records are dated to the whole second, and a turn can start before the daemon's or the host's answer marks the reply sent, so the bound is the second in which the user pressed Send, not the moment the reply counted as sent. That turn start also acknowledges the completion (below), so the result usually leaves the queue in the same scan; when it stays, its row note is still "Sent, waiting for Codex" ("Sent, not confirmed" for Claude), never that the session is working, since that turn may already be over. The card still never sends again.
- **unconfirmed** — ten seconds passed with no turn started after the send. Row note: "Sent, not confirmed". A turn start found later still moves the reply to confirmed.
- **failed** — the daemon refused the request or the write never left. Row note: "Not delivered · reply in Codex" (or Claude), with Open beside it; Herdly will not retry.

No phase but `.ready` sends anything, no timer sends anything, and a failure is final: Herdly never resends a prompt it cannot prove failed to arrive. Progress is in memory, so after a restart the result has no note and nothing is re-sent; a restored result does not pop a card.

## Sending is not acknowledgment

Sending leaves the completion exactly where it was: a send Codex never takes acknowledges nothing. Seeing the card, "Show all" and the fold after a send acknowledge nothing either. Amended on 2026-10-08: once Codex records the turn the reply started (its `UserPromptSubmit`), that turn start acknowledges the session's earlier completions, as any prompt in a CLI session does ([product behavior](product.md)). The card then leaves the queue and the session shows as working.

Live walkthrough, once a daemon is running (`codex app-server daemon start`):

1. Finish a turn in a CLI session attached to the daemon and switch away. Expect: the result card with the message, a live "› Reply to this session" field, and Open and Dismiss.
2. Type "now add tests" and press Enter. Expect: the card folds at once; opening the queue shows the result row with "Sent, waiting for Codex", then the result leaving the queue and the session shown as working, and that prompt as the next turn in Codex — in that session and no other.
3. If Codex never records the turn, the completion stays on the queue until it is dismissed or its tab is visited.
4. Stop the daemon and finish another turn. Expect: the card with no reply field and no reason line, only Open and Dismiss.
