## Name

The product is named Herdly (domain herdly.app), renamed from Steer on 2026-10-20. The rename is a clean break: the bundle identifier, Application Support folder, hook markers, helper and terminal-title prefix all changed, and nothing migrates from a Steer install (see [Install](install.md#upgrading-from-steer)).

## Current handed-back reminder behavior

Keep Continue in Codex after no-decision handoff, with only Open in Codex. Remove a reminder on evidence that its exact request was resolved: Codex's recorded output for that turn and command (allowed, rejected, or interrupted), structured completion or cancellation of its exact session and turn, or the end of its session. Other turns and other requests remain queued. Presence does not prove approval is still pending, and the row says so: it was handed back with no decision and Herdly has not seen an answer yet. Open in Codex on an actionable CLI request hands back at once so Codex's own prompt appears immediately. Accessibility labels and keyboard interaction are covered by [notch placement](notch-placement.md). This supersedes older permission-still-needed wording below. See [approval reconciliation](approval-reconciliation.md).


## Platform

macos

Herdly is a native macOS app rendering the macOS design language (SwiftUI content inside AppKit panels and windows). Design tooling that only recognizes web, iOS, or Android must not treat this project as web; when guidance is needed, adapt Apple's macOS Human Interface Guidelines, not iOS. See [the platform decision](adr/0003-use-native-macos-ui.md).

## Users

The primary user is the project owner: a developer who runs several Codex sessions at once in the Codex desktop app and in Codex CLI inside Ghostty, and who works in other applications while those sessions run. The job is to know, at a glance and without leaving the current app, which sessions are working, which need an answer, and which have finished, and to get back to the exact session when they choose to.

Other Mac developers with the same setup are a secondary audience once the MVP is proven. Future work should not yet assume unfamiliar users, marketing, or a public first-run flow.

## Product Purpose

Herdly keeps the user aware of Codex work while they use other applications. It shows activity and requests for attention in a compact notch panel and lets the user return to the originating session. It exists because Codex's own surfaces only inform the user while they are looking at them.

Success is that the user keeps using Codex exactly as before, never misses an approval or completion while away, and never has Herdly approve, dismiss, or mark anything read on their behalf without evidence.

## Positioning

Herdly is a safe, exact companion. It never approves automatically, never claims a result was read without a verified signal, and returns the user to the exact session or Ghostty tab rather than to an app. Trustworthiness outranks feature breadth. A general agent dashboard, Codex's own notifications, or Notification Center could not truthfully make the same claim about handoff, acknowledgment, and exact targeting.

## Operating Context

- macOS 14 or later on a Mac, typically with a built-in notch display, sometimes with a second display.
- Codex desktop app (installed bundle identifies as com.openai.codex) and Codex CLI running directly in Ghostty, one session per unsplit tab.
- Herdly runs as a background menu-bar app (LSUIElement) with a status item, a controls window, and the notch panel. It observes native app activation, Herdly-owned Codex lifecycle hooks, and Ghostty tab titles carrying Codex's session ID.
- Launch at login is off until the user explicitly opts in. Its setting reflects macOS's ServiceManagement registration, including approval-required and unavailable states, rather than a saved Herdly preference. A registered login launch is quiet: it does not open the controls window, while the menu-bar item and notch retain their normal behavior.
- Verification rituals: `swift test`, the ad-hoc build script, isolated hook labs and probe scripts under `scripts/`, and human walkthroughs recorded as evidence. Agreed behavior in this file is authoritative; a draft integration is not a proven capability.

## Capabilities and Constraints

Build a fresh native macOS app with SwiftUI and AppKit. Keep session and queue rules (HerdlyCore) separate from the platform interface (HerdlyApp). Other operating systems are outside the initial scope.

Confirmed capabilities and rules are detailed in the sections below and in the [domain glossary](../CONTEXT.md): one shared notch on the active display, separate working and to-check counts, a prioritized attention queue, 30-second approval handoff, completion popups that stay open for the card-open time (3 seconds by default) with a mutable sound, local persistence across restarts, and exact return to a desktop task or unsplit Ghostty tab.

Terminology is fixed by the glossary: companion, Codex surface, notch, Codex session, approval request, Open in Codex, attention queue, acknowledged completion, uncertain completion, resolution evidence.

Undecided product facts: exact desktop conversation focus; Ghostty split panes; the items listed under Open decisions below.

## Product Principles

1. Preserve the Codex workflow: Codex stays fully usable when Herdly is closed, and Herdly never alters the user's real hook or permission configuration to test itself.
2. Fail closed: a timeout, error, or uncertainty never approves, never dismisses, and never marks anything read.
3. Say only what is known: the interface distinguishes verified state from uncertain state and never invents a missing reason, name, or read status. One agreed exception: an Open fallback looks like any other Open ([ADR 0015](adr/0015-raise-the-terminal-app-when-open-cannot-reach-the-exact-target.md)).
4. Exact, else the app, never arbitrary: return the user to the precise session or tab; when only the session's terminal app can be reached, raise that app (an Open fallback, [ADR 0015](adr/0015-raise-the-terminal-app-when-open-cannot-reach-the-exact-target.md)); otherwise say Open is unavailable. Never select an arbitrary tab or pane, and never treat a fallback as a visit or an input target.
5. Attention, not control: the queue orders what the user sees; it never serializes or supervises Codex execution.

## Accessibility & Inclusion

Keyboard and VoiceOver operation of the notch panel are in scope: every row and button carries a label naming its action and subject, Tab moves through controls once the panel is key, Up and Down arrows select a row in the open queue (drawn with the focus ring and spoken as selected) and Return opens a selected approval or question as its clicked card, Escape collapses without dismissing (on a clicked card the first Escape returns to the queue and a second collapses, agreed 2026-10-21, D6), and long commands read in full. Agreed with the user on 2026-11-13 ([#427](https://github.com/r-curio/herdly/issues/427), Paper L "2 · Keyboard in" and "4 · Sent", K "A · Hotkey"): one global hotkey, ⌃⌥Space by default, puts the keyboard in the notch from any app without a click. It is the only key Herdly claims system-wide; plain 1–9 and every other key stay with the app in front. With a spotlight card showing, the hotkey gives that card the keyboard; otherwise it opens the queue with its top row selected and a foot line naming the keys ("↑↓ select · ⏎ open · esc close · ⌃⌥Space hide"), and that queue stays open while the keyboard is in it, as a draft holds a card. Pressing the hotkey again, Escape at the top level, or the panel folding for any reason gives the keyboard back to the app that had it when the hotkey was pressed, at the same cursor; if that app has quit, Herdly activates nothing and macOS chooses, and an app that came forward meanwhile (an Open from the notch) keeps it. Keyboard focus pauses no countdown: ADR 0020 is unchanged. Settings › Notch has a Keyboard row with a shortcut recorder and an off switch; changes take effect at once. A shortcut another app already holds is reported there and the notch stays click-only. Placement follows the pointer's display unless the user has pinned a display.

## Initial supported surfaces

Support the Codex desktop app and Codex CLI running directly in Ghostty first. Map [#197](https://github.com/r-curio/herdly/issues/197) widens CLI support, for Codex CLI and Claude Code, to iTerm2, Terminal.app and WezTerm tabs and to tmux, Zellij and herdr panes hosted in any of them, under ADRs [0013](adr/0013-bind-cli-sessions-to-terminal-tabs-by-tty.md) to [0017](adr/0017-type-question-digits-and-replies-into-one-bound-pane.md) and the terminal host presentation below; each host ships once its acceptance run in [MVP acceptance](mvp-acceptance.md) passes. Warp, kitty, Alacritty, editors and IDEs, iTerm2's tmux control mode, and split panes stay outside the scope.

Monitor only Codex sessions running locally on the user's Mac in the first version. Remote Codex sessions, including sessions reached through SSH, are outside the initial scope. No remote session connection layer is required.

For the initial Ghostty scope, support one Codex session in an unsplit tab and return to that exact tab in its window. Multiple panes within a tab are deferred. Split tabs are unsupported for exact targeting; Open raises Ghostty without selecting a pane ([ADR 0015](adr/0015-raise-the-terminal-app-when-open-cannot-reach-the-exact-target.md)). Stable Ghostty remains the baseline; a prerelease is not required merely to support splits. Session-to-tab binding still needs verification, including two tabs in the same project. See ADR 0004.

The user's reference to ChatGPT desktop means its Codex work, not regular ChatGPT conversations. The installed /Applications/ChatGPT.app bundle identifies as com.openai.codex; scope remains Codex only. Available runtime integration points still require verification rather than assuming all desktop hosts expose the same capabilities.

## Agreed visibility behavior

Keep the Herdly notch visible in every app, including Codex desktop and Codex CLI, even when there is no running activity or attention item. Foreground changes do not hide the strip or its queue. Notification popup and sound eligibility remain separate from notch visibility. Exact desktop conversation focus is deferred.

Keep desktop completions queued until explicitly dismissed or the desktop app records them read, as described below. No app activation or navigation result by itself marks a completion read.

Terminal support retains its separate exact-pane requirement: using terminal pane B does not acknowledge activity from pane A. The shared notch remains visible while either Codex surface is active; visibility does not clear terminal items. Agreed on 2026-10-11: every terminal host, Ghostty included, acknowledges a CLI completion the same way, by a verified Open, a switch to its exact tab or pane, or five seconds of that tab or pane staying in front after the completion arrived ([ADR 0016](adr/0016-open-and-acknowledge-visits-the-same-way-on-every-terminal-host.md)).

If app activation or the required Ghostty pane identity is unknown, retain queue items without acknowledgment and leave approvals in Codex's normal flow. Unknown desktop activation retains the indicator rather than guessing it was viewed. Release any pending approval interaction with no decision on uncertainty; only Open in Codex remains. App-level visibility alone does not establish safe direct desktop approval support.

Present one shared notch on the display the user is actively using. On a display without a physical notch, use a compact top-center panel. Do not duplicate the queue across displays. The active display is the one under the pointer, unless the user has pinned the notch to one display in the Display section of Settings › Notch or the menu bar item. A pinned display is used wherever the pointer is; while it is not connected the notch shows on the built-in display (or follows the pointer when there is no built-in display) and returns to the pinned display when it reconnects, with the pin kept. While the user is interacting with the panel (pointer over it, or keyboard focus in it while a draft is in progress or VoiceOver is running) placement stays on the panel's current display, and a display that disconnects is never chosen. Display changes and interaction never change the queue, replay a notification, or extend an approval deadline. See [notch placement and keyboard interaction](notch-placement.md).

## Agreed queue experience

Use one shared notch for multiple Codex sessions. Its compact state is a black strip fused to the bottom of the menu bar, a little wider than the camera housing, showing three readings on one line: a pixel sprite per session, the animal the user chose in Herdly's settings drawn in that session's color, that steps while the session is working and stands still otherwise, the task name of the top-priority item (Codex's task name when it provided one, otherwise the shortened session identifier), and a badge counting items to check, hidden at zero. Agreed with the user on 2026-10-21 (D2, D3, D22; #318): the strip shows at most three sprites and nothing counts the sessions beyond them, which appear only in the open queue; while the queue is open the left wing shows one sprite, stepping while any session works, and the badge reads "N to check", still hidden at zero. With no session listed the strip shows an unlit gray sprite instead of a session's, and the open queue says "Nothing running" with the sources Herdly is listening to, or "Not connected" with a way into Herdly's controls when neither Codex nor Claude is connected. To check counts pending approval requests, including requests handed back to Codex, unknown Claude waiting sessions, and unacknowledged completions that have not moved under Earlier. Hovering the strip expands the queue with approval requests ahead of other activity, and it collapses shortly after the pointer leaves; clicking gives the panel keyboard focus but does not keep it open once the pointer leaves, except while unsent text is in a field on screen or VoiceOver is running (agreed with the user on 2026-11-03, [#376](https://github.com/r-curio/herdly/issues/376)). When it folds with focus, typing returns to the app the user was using. This is a queue for the user's attention; it does not serialize Codex execution.

Each approval request has its own 30-second handoff timer starting when the companion receives the request, including while it waits behind other requests. Opening the queue or reaching the request does not restart or extend its timer. Agreed with the user on 2026-10-23 (ADR 0020): while the pointer is on the notch, every live approval Herdly can decide stops counting down and resumes with the time it had left once the pointer leaves, but none stays open past 2 minutes from receipt. Keyboard focus alone does not pause it. Expired requests retain only Open in Codex while permission is still needed.

Queue priority is: actionable notch approvals, question requests waiting for the user's answer, requests handed back to Codex that still need an answer, unknown Claude waiting sessions, unacknowledged completions (Earlier ones after recent ones), Claude sessions whose status is unavailable, then running tasks. Within each group, order by original arrival time, oldest first, except actionable notch approvals, which are ordered by the soonest deadline, then arrival (D12, agreed 2026-10-21, #314; this changes the oldest-first rule for approvals only). The strip and everything else that reads queue priority follow that order; which fresh request opens the spotlight on arrival is still the one that arrived first. Agreed with the user on 2026-10-11 (#182): a status-unavailable row stays below every completion, Earlier included, even though the to-check badge counts it and State grouping lists it under "Needs you". A status-unavailable row has no arrival time, so several of them keep a stable order by session rather than by age. A concrete approval or question for a Claude session replaces its generic waiting row so the same session is not counted twice. Expiration moves a request into the handed-back group without restarting its timer.

Each open-queue row is headed by one line, agreed with the user on 2026-10-21 (D17, D21, D14; #314), replacing the 2026-10-09 heading with its source tag and kind tags: the session's mark, its name, a dim "· repo @ branch" place when Herdly has seen the session's working directory, at most one word, and an age lane on the right (time since the row's latest evidence, "<1m", "4m", "2h", "3d"). The row no longer names its source; a question row's second line still does. A live approval shows "Ns left" instead of a word (below). Every other row carries a word only when it is off its normal path: "Failed", "Handed back", "Waiting", or "Status unknown" (a result whose status is unavailable reads "Status unknown" too). A result row whose session Herdly cannot open reads "Unreachable" (#322, Paper 8J1); it takes the one word slot ahead of "Failed", "Waiting", or "Status unknown", because it decides whether the row can be clicked, and VoiceOver still reads the full state it replaces ("Codex failed"). Approve, answer, check, and a stopped result get no word, because the section heading already says the kind, and a working row has none; the mark stepping is the only working signal. Red marks only failures: "Failed" sits in a dark red well, and every other word is plain dim text (D14). A status-unavailable row has no arrival time, so its age lane shows "—" and VoiceOver reads "No update time". VoiceOver reads each row's name, place, row note when one shows, and full state ("Permission needed"), and a live approval's seconds left. The place follows the display profile's label format (D21): "Repo @ branch" (the default), "Repo", or "Branch", chosen under After each name in Settings › Notch, per display profile (#324). A part Herdly has not seen is left out, so Branch with no known branch shows nothing, and a long place ends in an ellipsis. A Claude session's directory comes from its agents inventory. The branch is read from the working tree's `.git/HEAD` during each scan; a missing, unreadable, or unparseable HEAD shows the project without a branch. None of these readings identifies a navigation target, and the age is not an approval deadline.

A live approval's "Ns left" (D7, D12) counts down the request's own 30-second window in whole seconds, rounded up, refreshed every second, with a bar under it as long as the share of the window left. The approval card shows the same reading as its countdown row: the bar full width and "18s left" after it, bright for the last five seconds (#320). It only reads the deadline: opening the queue or the card, or reaching the row never moves it. While the pointer is on the notch the reading and its bar stand still (ADR 0020).

This priority order is the default, "Sort by: By need" (D25, agreed 2026-10-21; formerly "Needs attention"). The user can choose "Sort by: Newest first" (formerly "Last update") in Herdly's settings instead; only the labels changed. In both sorts live approvals stay first in their priority order, soonest deadline first (a request seen twice keeps its earliest deadline), then by arrival (D12), with question requests waiting for the user's answer next, so a request can't drop below newer activity while its timer runs. Under Newest first every other row is ordered by its most recent event, newest first; this includes status-unavailable rows, which are not pinned and are dated to the moment the queue is read, so they normally lead the unpinned rows. Results that have moved under "Earlier" stay together at the end of the queue, newest first, so they fold under one heading. The sort setting changes only the order of the open queue. Neither it nor the deadline order changes Codex's execution order or any deadline, and the sort doesn't change which item the strip names, which sessions get the strip's sprites and colors, what is spotlit, the counts, or any approval deadline.

Agreed with the user on 2026-10-09: the open queue shows what needs the user first and keeps sessions that are only working out of the way. Every row that needs the user (approvals, questions, handed-back requests, unknown Claude waiting sessions, status-unavailable sessions, and unacknowledged completions, Earlier included) is listed first, in the chosen sort order. While any such row is listed, running rows fold behind one "N working" line below them, closed each time the panel opens. Opening the fold shows them in the same sort order. With State grouping the fold replaces the "Working" heading. Agent and Project headings repeat inside the fold. When nothing needs the user, running rows are the queue and show unfolded, under a "Working" heading with their count when the queue is not grouped (#319, F1–F3, agreed 2026-10-21). The fold changes presentation only: not the counts, the strip, the spotlight, acknowledgment, or any deadline.

Agreed with the user on 2026-10-21 (D13; #314), replacing the "Needs you" heading: with no grouping, the rows that need the user sit under kind sections, "Approve N" (live approvals), "Answer N" (waiting questions), and "Check N" (everything else that needs the user), each heading with its count; an empty section and its heading disappear. So that a busy queue still reads at a glance, later sections fold their extra rows behind "+N more". Sections and folds change presentation only: not the counts, the strip, the spotlight, acknowledgment, or any deadline.

Discovery only ever adds a running row; a completion, request, question, or sound still needs its own evidence. See [session discovery](session-discovery.md).

Codex's own background jobs are not the user's work and get no working row or completion. Agreed with the user on 2026-10-08 for memory consolidation, which Codex runs as a session of its own and was seen ending without a turn or session end, and on 2026-10-21 for the desktop app's next-message suggestion, which runs after each finished turn. Clicking it, or Return on it when selected, opens it in place; one row is open at a time, and a second click or Escape closes it (Escape collapses the panel only when no row is open). With no running subagents the opened row has no switcher. The switcher exists only in an opened row: the queue row, strip, counts, spotlight and acknowledgment are unchanged, and approval cards do not name the subagent that asked. Opening a row acknowledges nothing. Missing or malformed tool data adds no action. Tool activity changes presentation only: it never changes attention priority, acknowledgment, or an approval deadline. Actions are not restored across a companion restart; a new tool event must arrive first. The installed payload shapes are recorded in [tool activity evidence](evidence/tool-activity.json).

## Agreed mixed-source notch behavior

The notch presents Codex and Claude observations in one priority queue. Every row names its
source explicitly. Open in Codex and Open in Claude are the action's names; its visible label is "Open Session" (agreed 2026-10-08), except in three places that read plain "Open": an opened running row (#319), an approval row's "Not delivered · answer in Claude" note, and a live approval card beside Approve and Deny; a handed-back approval card reads "Open in Codex" or "Open in Claude" (#320). VoiceOver reads "Open Session: <subject>" everywhere. Claude cards explain when returning to the exact
tab is unavailable and show Open in Claude only after Ghostty controls, a complete live Claude
inventory, and one exact unsplit target are verified. Claude
uses its supplied session name for display when available and otherwise shows a shortened session
identifier. Since 2026-10-21 (D17; #314) an open-queue row no longer names its source: the row is the
session's name and place, and a question row's second line names its source; the spotlight keeps the
prefixed label. The name is presentation metadata and does
not identify a target or claim who supplied it. Live rows read Working or Waiting. A finished, failed,
or stopped turn keeps that terminal label; when the current or terminal state cannot be classified,
the row says Status unavailable.

Requested by the user on 2026-10-15: a Claude row that looks stuck carries a Remove action, so a row

## Agreed work status on finished rows

Agreed on 2026-11-13 ([#417](https://github.com/r-curio/herdly/issues/417), Paper journey board "I · Finished verdict and stuck sessions", and the Herdly Settings page "GitHub status in Agents"). A finished row can say how far its session's work got (its **work status**, see [CONTEXT.md](../CONTEXT.md)): uncommitted, not pushed, checks running, checks failing, conflict, checks passed, or merged. Herdly reports facts and never judges the code. Anything it cannot establish has no verdict, never a guess. ADR 0023 records the boundary.

- **Which branch.** The verdict is about the branch Herdly saw the session on while the turn ran, remembered so it still resolves after an agent merges and the folder returns to the default branch. There is no verdict when:
  - the branch or folder changed during the turn;
  - another live session was in the same folder during the turn: working, waiting, or holding an approval, question or handed-back request;
  - Herdly never saw the turn running, as with rows restored after a restart.
  A detached HEAD gets no pull request.
- **Reading.** Read-only git in the session's folder gives uncommitted and not pushed. The GitHub CLI (`gh`), with the user's own sign-in, gives the branch's pull request, including one already merged, with its mergeability and checks.
  - **Order.** A merge after the turn started comes first. Next, while the folder is still on that branch, uncommitted changes, then unpushed commits. Then the open pull request: conflict, checks failing, running, or passed.
  - **Failures.** A missing, signed-out, offline, rate-limited or failing `gh`, a repository not on GitHub, no pull request, or more than one open pull request for the branch: Herdly gives what local git established, or nothing. It never shows an error in the notch.
  - **Merged after the branch is deleted.** A merged pull request is still found by its branch after the branch is deleted ([evidence](evidence/github-pr-status.md)). If it cannot be read, the row says nothing.
- **Refresh.** Herdly reads a finished row once when it appears, then again only while its checks run: every 30 seconds, for at most an hour from the first reading. Every other verdict is final for that row, recent or Earlier. A "checks passed" row is not re-read to catch a later merge. One exception: while GitHub is still working something out (mergeability not computed yet, no checks registered yet, or a pushed branch whose pull request is not listed yet), Herdly reads again every 30 seconds for up to 5 minutes from the first reading, then settles on what is certain. A finished row reads no verdict while any row of its own session's turn is still live, including a handed-back reminder that outlives the turn. A reading is dropped when such a row comes back, and re-read once it ends, within the original hour.
- **Switch.** "Pull request status on finished rows" on the GitHub card in Settings › Agents. It is on by default while `gh` is installed and signed in. Off, Herdly runs no git or `gh` process at all, the card's own check included, and forgets what it read. The card then shows the last check, or not installed when `gh` is missing on disk, or Status unknown. Signed out and not installed show `gh auth login` or `brew install gh` with Copy. Herdly never runs either.
- **Presentation (agreed; drawn by the follow-up, [#418](https://github.com/r-curio/herdly/issues/418)).** Once Herdly knows how far a finished session's work got, the row's dim place becomes the state, then the pull request: "· checks failing · herdly#431". With no pull request it is the state, then repo @ branch. With no verdict the row keeps "· repo @ branch" as today. Only the state words take a tone: red for checks failing and conflict, amber for uncommitted, not pushed and quiet, gray for checks running, green for checks passed and merged. #417 reads the verdict and draws nothing in the notch.
- **Unchanged.** A verdict never changes queue order, counts, acknowledgment, the spotlight, or any approval deadline.

### Settings

**Layout.** The Terminals page has two sections. **Terminals** lists Ghostty, iTerm2, Terminal.app and WezTerm. **Multiplexers** lists tmux, Zellij and herdr. Each section is one card with one row per shown app, and each app has its own switch; Herdly scans and contacts only what is switched on. herdr gains a switch: on upgrade it starts in the position of the Ghostty switch, so existing behavior is unchanged. Every other new switch starts off.

**Card.** Agreed 2026-10-21 (#317, D31/D32): each app is one row in its section's card, with inset dividers between apps and no footer. A row shows:

- **Name and version.** The installed version in dim text after the name, for information only. Herdly checks the capabilities it needs (such as Ghostty's `tty`) rather than comparing version numbers. The one hard floor is Zellij 0.44.1, which is needed for `focus-pane-id` and `--pane-id`. A message names a version only once a release has been verified to provide the capability.
- **Status badge.** Off while the switch is off. Not in use while nothing has been seen there. Otherwise Ready or Needs attention.
- **Switch.** Off means Herdly never scans or contacts that app.
- **⋯ menu** with **Show Diagnostics…** and **How Open Works…**.
- **Problem lines** beneath the row, only when something needs fixing: every problem that applies, one per line, because each is a separate fix. Commands come with a Copy button; Herdly never runs them or edits the app's configuration.

**Permission** (iTerm2, Terminal.app and Ghostty only). These need macOS Automation access and follow Ghostty's existing flow: turning the switch on asks macOS; a denial turns the switch back off and offers Open Settings…; if the app isn't running, Herdly asks when it next launches. There is no separate Permission row: Allowed shows as Ready once the app is in use (for Ghostty, once a scan has read it), Not allowed shows as a problem line with Open Settings… and Needs attention while the switch is on, and Not verified (not yet checked, the app not running, or consent not yet given) shows as Not in use. WezTerm and the multiplexers use command-line tools or sockets and have no permission line.

**How Open Works…** opens a sheet with the app's targeting rule and what Open does otherwise, for example "Herdly returns to unsplit tabs; otherwise Open raises iTerm2." Because an Open fallback is silent on the card (ADR 0015), this is where it is explained.

**Show Diagnostics…** opens a sheet with the exact internal reasons an app's integration records, such as the scan's result and, for each queued session in that app, its Open availability, its last Open result (verified, fallback or unavailable) with the reason, and why typed input is unavailable. It is disabled while there is nothing to show; Ghostty records none today, so its item is always disabled.

**Problem lines.**

- **Every app:** not found in its fixed locations; can't be read (a scripting error, Automation denied, a socket that is missing or fails its trust check).
- **A switched-off app holding sessions:** once Herdly sees a live Claude session whose process ancestry reaches an installed app that is switched off, its row says sessions were seen there and offers to turn it on. Ancestry needs no Automation access.
- **Multiplexer with no terminal on:** the switch stays usable, the badge reads Needs attention, and the line says "Turn on the terminal you run tmux in." (naming that multiplexer). Herdly contacts a multiplexer only while a terminal is also on (ADR 0014).
- **tmux:** sessions seen on a socket other than the default can't be reached.
- **Zellij:** older than 0.44.1; more than one `zellij` client process running.
- **herdr:** its Claude integration missing or not current while Herdly has seen Claude in herdr: the exact `herdr integration install claude` command. herdr unavailable (not running, unsupported protocol, untrusted socket and similar): generic wording. Until ADR 0009's gate opens, Herdly does not contact herdr and the badge reads Not in use.
- **Ghostty without `tty`:** "Update Ghostty", decided by checking that Ghostty exposes each terminal's `tty`. ADR 0011's sole-terminal rule still applies; a second Ghostty tab, window or quick terminal brings this guidance back.

## Integration findings

Codex's documented PermissionRequest hook runs before the normal approval prompt. It can return allow or deny, or leave the decision to Codex's normal approval flow. A hook-based notch approval therefore needs an explicit handoff policy; simultaneous actionable prompts in the notch and Codex are not established by this interface. Source: https://learn.chatgpt.com/docs/hooks#permissionrequest (checked 2026-09-11).

This is an integration finding, not a selected transport. Desktop app and CLI behavior still require separate verification.

Codex runs hooks only when `features.hooks = true` is set in config.toml, and runs a non-managed hook only after its exact definition is trusted; trust is recorded per handler in config.toml as `[hooks.state."<hooks.json path>:<event>:<group>:<handler>"] trusted_hash = "sha256:…"`, a SHA-256 of the canonical JSON of the normalized handler (SessionEnd timeouts clamp to 3 s before hashing). Configure Codex sets the feature flag and records trust for exactly the handlers it installs, since the user approved them in the preview; a hook Codex marks as changed reads as repair-required. Verified against seven entries recorded by CLI 0.145.0 and the desktop app's bundled 0.153.4 (checked 2026-09-14). Codex desktop also rewrites config.toml on its own, so Herdly owns only its lines and hook entries: status checks their presence, reinstall re-baselines on the current files, and undo removes exactly Herdly's additions, restoring the original files verbatim only when they are still byte-identical to the install.

The documented app-server thread/read method retrieves conversation data; it is not a user-view receipt. No authoritative user-view notification was established in the reviewed app-server reference. Exact desktop focus is deferred; Ghostty pane focus still requires technical verification. Source: https://learn.chatgpt.com/docs/app-server (checked 2026-09-11).

The [first desktop investigation](codex-desktop-investigation.md) found private conversation-level read-state events in the installed app and confirmed lifecycle/approval protocol definitions with a runnable probe. The user subsequently verified task-link navigation from Codex and Apple Notes. App-level visibility still needs live implementation verification, and approval handoff remains unverified; computer-use access to Codex was blocked.
